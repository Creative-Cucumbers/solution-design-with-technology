## 5. ソフトウェア開発方法論とは / なぜ必要か (6分)

### 5.1 開発方法論とは「作り方の型」

**ソフトウェア開発方法論**とは、次のようなことを決めた**作り方の型**です。

- **何を作るか**をどう決めるか
- **どの順で**進めるか
- **誰が何を**やるか
- **どこまでできたら完成**とするか

コードの書き方の話ではありません。**進め方**の話です。

### 5.2 なぜ必要か: 決めていないと起きること

ホワイトボードを見てください。いま出てきたものは、全部**「作り方が決まっていないと起きること」**です。

| さっき出た問題 | 方法論ではこう呼ばれている |
| --- | --- |
| 何を作るつもりだったか言葉になっていない | **要件定義 / 仕様** |
| どこまでできたら完成か決まっていない | **受け入れ条件 / 完成の定義** |
| 後から要求が来ると崩れる | **反復（イテレーション）と優先順位付け** |
| 他の人に説明できない | **ドキュメント / レビュー** |
| 本当に動くか確かめていない | **テスト** |

**受け入れ条件と完成の定義は、関係していますが別のものです。**

- **受け入れ条件**: その機能が満たすべき具体的な条件。例：「残り3分になったら表示の色が変わる」
- **完成の定義（DoD）**: 成果物が完成と呼べるための、共通の品質基準。例：「必要なテストとレビューを終え、利用できる状態になっている」

この演習では、まず機能ごとの受け入れ条件を書く練習をします。

これらは、みなさんが今日初めてぶつかった問題ではありません。**同じことで困った人たちが、50年以上かけて型を作ってきました。**

### 5.3 ソフトウェア工学という領域

ソフトウェアの作り方そのものを研究する **ソフトウェア工学（Software Engineering）** という学問領域があります。世界中で「どうすればよりよく開発できるか」というプロセスの見直しと改善が今も続いています。今日扱うウォーターフォールやアジャイルも、その積み重ねの中で生まれてきたものです。

### 5.4 方法論の地図

方法論には、**一人でも効くもの**と**チームで効くもの**があります。

```mermaid

    subgraph solo["一人〜小規模でも効く型"]
        A1["仕様駆動開発<br/>SDD"]
        A2["テスト駆動開発<br/>TDD"]
    end
    subgraph team["チームで効く型"]
        B1["ウォーターフォール"]
        B2["アジャイル<br/>スクラム / XP"]
        B3["リーン"]
        B4["DevOps"]
    end
    classDef default fill:#f3f4f6,stroke:#1f2937,color:#111827;
```

開発の進め方は、一つの方法が次の方法に置き換わる形で発展してきたわけではありません。古くからある実践を見直したり、組み合わせたりしながら発展してきました。以下は、歴史上の代表的な出来事です。

| 時期 | 代表的な出来事 |
| --- | --- |
| 1950年代以降 | 反復・漸進的に開発する実践が見られる |
| 1970年代 | 段階的な開発プロセスについて議論が進む |
| 1990年代 | スクラムやXPなどの実践が発展する |
| 2001年 | アジャイルソフトウェア開発宣言がまとめられる |
| 2009年ごろ | DevOpsという名称で、開発と運用の協働が広まる |
| 近年 | 生成AIを利用した開発や、仕様を中心にAIと開発を進めるツールが広がる |

**仕様を明確にして開発する考え方自体は、生成AIより前からあります。** 今日扱うGitHub Spec Kitは、その考え方をAIとの開発に取り入れるツールの一つです。

今日は、**さっき詰まった所に一番効く型**から見ていきます。地図の左側、一人でも効く「仕様駆動開発」です。チーム側の型は、9節でもう一度詰まってもらった後に扱います。

### 5.5 銀の弾丸はない

先に大事なことを言っておきます。**どの方法論が正解、というものはありません。**

選ぶときの軸は2つです。

- **何が不確かなのか**（作るものが決まっているのか、誰が使うかも分からないのか）
- **失敗のコストはどれくらいか**（作り直せるのか、人命や法律が関わるのか）

## 6. 方法論の一つ: 仕様駆動開発 (6分)

### 6.1 バイブコーディングが得意なこと

AIに話しかけて勢いで作るやり方を **バイブコーディング（vibe coding）** と呼びます。今日はこれを否定しに来たのではありません。得意なことがはっきりあります。

- **速い**。ゼロから動くものが数分で出てくる
- **試すのに向く**。捨てる前提のアイデア検証には最適
- **一人で完結する**。誰とも相談しなくていい

問題は、**それしか持っていない**ことです。

### 6.2 仕様とは「頭の中の条件を書き留めたもの」

さっきの5つの条件は、講師の頭の中にありました。お客さんは、自分の要求を全部言ってはくれません。

**仕様（spec）とは、お客さんの頭の中にある条件を引き出して、書き留めたものです。**

「仕様書を書く」というと堅苦しく聞こえますが、やることは「後で揉めそうなことを先に紙に書く」だけです。

### 6.3 仕様駆動開発の流れ

**仕様駆動開発（SDD: Spec-Driven Development）** は、仕様を中心に置いて、その先を組み立てる進め方です。

```mermaid
graph LR
    S[仕様<br/>spec] --> P[計画<br/>plan] --> T[タスク<br/>tasks] --> I[実装<br/>implement] --> V[受け入れ条件<br/>で検証]
    V -.->|条件を満たさない| S
    classDef default fill:#f3f4f6,stroke:#1f2937,color:#111827;
```

大事なのは、**各段で人間が承認する**ことです。

> AIに丸投げするのではなく、**AIが出したものを人間がレビューする**。これが今の開発の形です。

### 6.4 使うツール: GitHub Spec Kit

この型を実際に使うために、**[GitHub Spec Kit](https://github.com/github/spec-kit)** を使います。2025年9月にGitHubが公開したツールキットで、GitHub Copilot / Claude Code / Gemini CLI / Cursor / **Antigravity** などで動きます。

配布した [starter](./starter) に最初から入っています。使うコマンドは4つです。

| コマンド | 何をするか |
| --- | --- |
| `/speckit-specify` | 仕様書（`spec.md`）を作る |
| `/speckit-plan` | 実装の計画（`plan.md`）を作る |
| `/speckit-tasks` | タスク一覧（`tasks.md`）を作る |
| `/speckit-implement` | タスクに沿って実装する |

### 7.1 受け入れ条件を自分で書く

ここはAIに任せません。**「どこまでできたら完成か」を決めるのは人間の仕事**です。

### 7.2 仕様書を作ってレビューする

> [!NOTE]
> **やること（5分）**
>
> 1. `/speckit-specify` に「お題 ＋ 自分で書いた受け入れ条件」を渡す
> 2. 生成された `spec.md` を**読んでレビューする**

>    - 足りない所、違う所を直す

`spec.md` は `specs/` フォルダの下に作られます。

### 7.3 計画・タスク・実装

> [!NOTE]
> **やること（6分）**
>
> 1. `/speckit-plan` → 計画（`plan.md`）ができる
> 2. `/speckit-tasks` → タスク一覧（`tasks.md`）ができる。**受け入れ条件がタスクに紐づいているか**を確認する
> 3. `/speckit-implement` → 実装が始まる

実装が走っている数分間は、待ちながら講師の話を聞いてください（現場での仕様駆動開発の話をします）。

**時間内に実装まで終わらなくても構いません。** 各段階で、何を入力し、どんな資料ができたかを確認してください。時間に合わせるためにレビューや承認を省略する必要はありません。

実装が間に合わない場合は、自分たちの仕様書を保存し、講師が配布するサンプル実装で受け入れ確認の手順を練習します。この場合、比較表には「サンプル使用」と記録し、自分たちの演習Bの結果と区別してください。

もう一度、**お互いの画面を見せ合ってください。** 演習Aのときより、2人の結果は近づいていますか？

終わった段階まで、手元を見てください。**`spec.md` / `plan.md` / `tasks.md` がファイルとして残ります。** 何を作るか、どう進めるかを記録することで、他の人が続きを作る際の手がかりになります。

## 11. チームで効くソフトウェア開発方法論 (10分)

5.4の地図に戻ります。今度は**チーム側**の型を開きます。

みなさんが出した「難しかったこと」は、次のように解かれてきました。

| さっき出た難しさ | 方法論での答え |
| --- | --- |
| 誰が何をやるか決まらない | スクラムの**責任の区分**（プロダクトオーナー / スクラムマスター / 開発者）とチームの自己管理 |
| 何をいつやるか分からない | **プロダクトバックログ**と**スプリント計画** |
| 状況が共有されない | **デイリースクラム**（ゴールへの進捗確認と計画の調整） |
| 完成の判断が合わない | **完成の定義（DoD）** と**受け入れ条件**（7節で書いたもの） |
| 同時に触って衝突する | **バージョン管理**・**CI/CD** |
| 同じ失敗を繰り返す | **レトロスペクティブ**（振り返り／4限目で体験します） |
| 工程ごとの成果物や承認を明確にしたい | **ウォーターフォール**などの段階的な進め方 |
| 手が空く人・無駄な作業が出る | **リーン** |

### 11.1 ウォーターフォール型

ウォーターフォール（滝）型は、直線的で順序立てたプロセスです。各フェーズが完了してから次に進み、前のフェーズに戻ることはあまり想定されていません。

```mermaid
graph TD
    A[要件定義] --> B[システム設計]
    B --> C[実装]
    C --> D[テスト]
    D --> E[展開]
    E --> F[保守]
    classDef default fill:#f3f4f6,stroke:#1f2937,color:#111827;
```

- **メリット**: 明確な段階と成果物があり、計画が管理しやすい
- **デメリット**: 変更に柔軟に対応しづらく、後戻りが難しい
- **採用しやすい場面**: 要求・技術・依存関係が比較的安定し、工程ごとの成果物や承認を明確にする必要がある場合
- **注意点**: 動くものを使った検証が後半に偏ると、要求の食い違いや技術上の問題に気づくのが遅くなる

### 11.2 アジャイル型

アジャイルは、動くソフトウェアを早く届け、顧客との対話やフィードバックを通じて、作るものと進め方を適応させていく考え方です。

その実践方法の一つが**スクラム**です。スクラムでは、**スプリント**という1か月以内の一定期間を繰り返し、その中で計画、開発、成果の検査、進め方の改善を行います。

以下の図は、スクラムを使った進め方の概略です。アジャイルのすべての実践が、スプリントを使うわけではありません。

```mermaid
graph TD
    A[プロダクトバックログ] --> B[スプリントプランニング]
    B --> C[設計・実装・テスト・デプロイ]
    C --> D[スプリントレビュー]
    D --> E[スプリントレトロスペクティブ]
    E --> B
    C --> F[リリース]
    classDef default fill:#f3f4f6,stroke:#1f2937,color:#111827;
```

スプリントプランニング、デイリースクラム、スプリントレビュー、スプリントレトロスペクティブは、すべてスプリントの中で行います。利用可能な成果物は、スプリントの終了を待たずにリリースすることもできます。

- **メリット**: 柔軟に変更対応ができ、早い段階で価値を提供できる
- **デメリット**: 長期的な計画が見えにくくなることがある
- **向く場面**: 誰がどう使うか不確かな新規サービス、ユーザーの反応を見ながら育てるもの
- **落とし穴**: 「計画しない言い訳」に使われる。反復すること自体が目的化する

#### スクラム: 役割・イベント・バックログ

アジャイルの代表的な進め方が**スクラム**です。演習Cで困ったことが、そのまま仕組みになっています。

| 要素 | 何か | 演習Cのどの困りごとに効くか |
| --- | --- | --- |
| プロダクトオーナー | プロダクトの価値を最大化する責任を持ち、目標やバックログの順序を明確にする | 「誰が決めるのか分からない」 |
| スクラムマスター | スクラムへの理解と実践を支援し、チームが効果的に働けるようにする | 「進め方を改善できない」 |
| 開発者 | 利用可能な成果物を作る。必要な作業の進め方を自分たちで決める | 「誰がどう作るか決まらない」 |
| プロダクトバックログ | プロダクトを改善するために必要なことを、順序を付けて並べた一覧 | 「何から手をつけるか揉める」 |
| スプリント | 1か月以内の一定期間。一般には1〜4週間で設定する | 「終わりが見えない」 |
| デイリースクラム | 開発者がスプリントゴールへの進捗を確認し、作業計画を調整する15分のイベント | 「進捗に合わせて計画を調整できない」 |
| スプリントレビュー | 関係者と成果や状況の変化を確認し、次に何をするかを話し合う | 「関係者と次の方向性が合わない」 |
| スプリントレトロスペクティブ | 品質とチームの有効性を高めるため、進め方を振り返って改善を計画する | 「同じ失敗を繰り返す」 |

#### アジャイルソフトウェア開発宣言

2001年に書かれた4つの価値観です。

- プロセスやツールよりも **個人と対話** を
- 包括的なドキュメントよりも **動くソフトウェア** を
- 契約交渉よりも **顧客との協調** を
- 計画に従うことよりも **変化への対応** を

> [!NOTE]
> プロセスやツール、ドキュメント、契約交渉、計画にも価値があります。そのうえで、**太字で示した「個人と対話」「動くソフトウェア」「顧客との協調」「変化への対応」に、より価値を置く**という宣言です。

#### XP（エクストリーム・プログラミング）

アジャイルの中でも、技術プラクティスを重視する進め方です。ペアプログラミング（2人で1台のPCを共有して書く）、テスト駆動開発、継続的インテグレーション、小さなリリースなどを組み合わせます。

今日の演習A・Bは、**それぞれのPCで作って結果を見比べる**形なので、厳密なペアプログラミングではありません。ただし「一人で抱え込まず、相談しながら進める」という点は同じです。

### 11.3 リーン型

無駄を省き、価値のある作業に集中することに重点を置く考え方です。製造業（トヨタ生産方式）から来ています。

- 顧客にとっての**価値を特定**する
- 価値が生まれる流れ（**バリューストリーム**）を可視化して、無駄を見つける
- 流れを滞らせない
- **継続的に改善**し続ける

新規事業では**リーンスタートアップ**として、「作る → 測る → 学ぶ」を小さく速く回す形で使われます。4限目で扱う **MVP（Minimum Viable Product）** はここから来た考え方です。

### 11.4 DevOps / CI・CD

**DevOps**は、開発と運用が協働し、ソフトウェアを継続的かつ安定して届け、動かし続けるための考え方や実践です。

- **CI（継続的インテグレーション）**: 変更を頻繁に統合し、自動ビルドやテストによって問題を早く見つける
- **継続的デリバリー（Continuous Delivery）**: 変更を検証し、いつでも本番へ出せる状態を維持する。本番へ出す判断は、人が行う場合もある
- **継続的デプロイ（Continuous Deployment）**: 必要な検証を通過した変更を、自動で本番へ反映する

後ろの2つは、どちらも「CD」と略されます。

演習Cで別々に作った機能を一つにまとめる作業は、インテグレーションです。CIは統合による問題の早期発見を助けますが、**機能のつなぎ方や競合の解決には、人による設計や調整も必要です。**

### 11.5 比較表と使い分け

| | 要件の確かさ | 進め方 | 価値が出る単位 | 変化への強さ | 向く場面 | 落とし穴 |
| --- | --- | --- | --- | --- | --- | --- |
| **ウォーターフォール** | 比較的安定している前提 | 段階を順に | 全体完成後の提供になりやすい | 変更時の調整が大きくなりやすい | 要求・技術が安定し、工程ごとの承認が必要 | 検証が後半に偏ると気づくのが遅い |
| **アジャイル（スクラムなど）** | 変化や不確実性を見込む | 反復して検査・適応 | 小さな成果を継続的に提供 | 変化に適応する機会を設ける | フィードバックを得ながら育てるサービス | 計画しない言い訳になる |
| **XP** | 決まっていない前提 | 短い反復＋技術規律 | 常に動く状態 | 強い | 少人数で品質も要る | 規律を守れないと崩れる |
| **リーン** | 仮説として扱う | 無駄を削る／学習を回す | 学びごと | 強い | 新規事業、業務改善 | 削りすぎて脆くなる |
| **DevOps** | （進め方と直交） | 自動化と協調 | リリースごと | 強い | 継続的に動かすサービス | 道具だけ入れて文化が変わらない |
| **仕様駆動（今回のAI利用例）** | 仕様として明文化し、必要に応じて更新 | 仕様→計画→タスク→実装→検証 | 検証済みの機能ごと | 仕様と実装を一緒に更新する必要がある | AIと作るものや進め方を共有する | 仕様を書いただけで正しさを保証したと思い込む |

**選ぶときの軸は2つ**でした（5.5）。

- **不確実性が高い場合**: 小さく試し、フィードバックを得る機会を増やす
- **要求や依存関係が安定している場合**: 事前計画や工程ごとの合意を活用する
- **失敗の影響が大きい場合**: 方法論にかかわらず、リスクに応じた設計・検証・レビューを厚くする

**期日が固定されていることや、規制があることだけで、方法論が一つに決まるわけではありません。** また、仕様駆動やDevOpsは、スクラムなどと組み合わせて使えます。

### 11.6 やってみよう: この案件、どう進める?

> [!NOTE]
> **挙手で答えてください（2分）**
>
> **ケースA**: 法改正に対応するための業務システム改修。期日は動かせず、必要な機能は全部決まっている。
>
> **ケースB**: 学内の困りごとを解決する新しいアプリ。誰がどう使うか、本当に使われるかは分からない。
>
> それぞれの案件で、**先に決めること、早く試すこと、途中で確認すること**を挙げてください。そのうえで、どの方法論や実践を組み合わせるか、その理由を説明してください。

みなさんがこの授業の第4回以降でやるのは、**ケースB**です。

## 13. マシュマロチャレンジとは (7分)

> 👨‍💼 **お客さん**: 大好きなマシュマロとパスタを使って塔を建てたい!
> 🏗 **お客さん**: 塔は高ければ高いほど良い!
> ✨ **お客さん**: マシュマロの位置は高ければ高いほど良い!

➡️ **どうする?**

### 13.1 ルール

1. **1チーム3〜5人で、作戦タイムも含めて18分**で行います
2. **自立可能で、できるだけ高いタワーを立て、タワーの上にマシュマロを置きます**（パスタに刺してもOK）
3. **テープで足場を固定してはいけません**
4. **パスタやテープ、ひもは切ったり貼ったりするのはOK。マシュマロは切ってはいけません**
5. **計測の最中もタワーが立っていなければ、記録になりません**

**この授業では、机の面からマシュマロの底までの高さを記録します。** [Tom Wujecの紹介するルール](https://www.tomwujec.com/marshmallow-challenge)では上端まで測りますが、今回は授業内の統一ルールとして底まで測ります。すべての計測で同じ基準を使います。

終了の合図でタワーから手を離してください。計測中も自立していることが必要です。

| --- | --- |

| 🏷 マスキングテープ | 90cm |

## 16. 解説: なぜこれをやったのか (14分)

ここで種明かしをします。**このゲームは、3限目に学んだことと同じ構造をしています。**

### 16.1 いま何をしていたのか

- 🎯 **顧客ニーズ**: マシュマロをより高く掲げるタワー
- 🍝 **手段**: パスタ・テープ・ひも
- 🛠 **解決方法**: 試行錯誤してタワーを立てる
- ⏱ **締切**: 18分

➡️ これは、限られた時間と材料で、チームが不確実な課題に取り組む**ソリューション開発の演習**です。ソフトウェア開発にも共通する、試行錯誤、協働、早期検証の重要性を体験できます。

### 16.2 マシュマロチャレンジとスクラムの対応

| 項目 | マシュマロチャレンジ | スクラム開発 |
| --- | --- | --- |
| **目標達成のプロセス** | 制限時間内に高いタワーを構築する | スプリント内で成果物を完成させる |
| **反復と改善** | 試行錯誤を繰り返して最適な形を探る | スプリントごとにプロセスを改善し続ける |
| **チームの協働** | 役割分担とアイデア共有で成果を上げる | チーム内で協力し、全員が責任を共有する |
| **柔軟性と適応力** | 失敗しても新しい方法をすぐ試す | 要件変更や課題に柔軟に対応する |

3限目で出てきた概念との共通点を見てみましょう。

- **18分の区切り**: 短い一定期間で取り組む、スプリントの考え方に対応
- **「自立して、マシュマロが上にある」**: この課題の受け入れ条件
- **計測**: 条件を満たしたか、どの程度の成果が得られたかを検証する活動

この演習は、スクラムの一部の考え方を体験するものです。スクラムの仕組み全体を再現しているわけではありません。

### 16.3 アジャイルの前提と Fail fast

アジャイル開発の前提は1つです。

> **事前にすべてを正確に予測し、計画することはできない**

パスタは細く、マシュマロは思ったより重い。**やってみるまで分からなかった**はずです。だからアジャイル開発では、**小さく作って、早く確かめて、直す**を繰り返します。

#### ⚡ Fail fast（速く失敗せよ）

ホワイトボードの「初めてマシュマロを載せた時間」を見てください。

| 早く載せたチーム | 遅く載せたチーム |
| --- | --- |
| 早い段階で「重い」「倒れる」と**分かった** | 最後まで**分からなかった** |
| 分かってから**直す時間が残っていた** | 崩れたときには**時間がなかった** |

**失敗そのものに価値があるのではありません。早く失敗すれば、直す時間が残るということです。** 逆に、最後の1分で崩れた失敗からは、何も直せません。

いま味わった「あと3分あれば直せたのに」という感覚が、**Fail fast** です。

#### MVP（Minimum Viable Product）

**MVP（Minimum Viable Product）**は、顧客や価値についての重要な仮説を、できるだけ少ない労力で検証し、学ぶためのものです。単に機能を少なくした製品という意味ではありません。

何を確かめたいのか、誰に試してもらうのか、どの結果を見て判断するのかを決めることが大切です。

> [!IMPORTANT]
> 低いタワーに先にマシュマロを載せる行為は、まず「この構造で重さを支えられるか」を確かめる試作です。**重要な仮説を小さく試す点が、MVPの考え方に通じています。**

### 16.4 だから、次にやること

スクラムでは、スプリントの最後に**スプリントレトロスペクティブ**を行い、品質や進め方を改善する方法を話し合います。

この演習でも、その考え方を取り入れて振り返りを行います。**次に試す改善を決めてから、同じ課題にもう一度取り組みましょう。**

### 20.1 TEDの知見: 幼稚園児・ファシリテーター・賞金

### 20.3 3限目とのつながり

今日やったことを並べてみます。

| マシュマロチャレンジ | 開発で対応する考え方 |
| --- | --- |
| 立っているタワー | **利用可能な成果物**（ソフトウェア開発では動くソフトウェア） |
| 「自立して、マシュマロが上にある」 | **受け入れ条件** |
| 計測 | **検証** |
| 18分の区切り（×2回） | **短い一定期間で取り組む**（スクラムではスプリント） |

3限目では要求を共有・記録・確認することを、4限目では振り返りを次の行動に生かすことを体験しました。結果が改善した場合も、しなかった場合も、**何を変え、何が分かったかを具体的に説明すること**が大切です。
