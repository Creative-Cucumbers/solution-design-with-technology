# 第7回 総合演習 Constitution

第6回で決めたソリューションを、第7回の授業時間内につくるためのプロジェクト憲法です。仕様書（`spec.md`）や計画（`plan.md`）を作るとき、AIはこの原則に従います。

チームごとに扱うテーマは違いますが、守る原則は全チーム共通です。

## Core Principles

### I. 受け入れ条件は1〜3項目（NON-NEGOTIABLE）

このプロジェクトの受け入れ条件は **1〜3項目**。4項目目は作らない。

**人間がチームで合意した「絞り込みシート」が原本**であり、仕様書・計画・実装はそこに書かれた条件だけを満たす。シートにない機能は、良さそうに見えても足さない。

成果物テンプレートのスライド8は、このシートの**要約**である。要約に載っていない確認例や制約があっても、シートに書かれていれば有効とする。

足したほうがよいと判断した場合は、**実装せずに提案だけする**。採用するかどうかは人間が決める。

**ただし、1つの条件に確認例を複数付けることは、条件を増やすことではない。** 同じ操作を2回したとき、別の対象に誤って反映しないかなど、その条件が正しく成立することを確かめる例は、必要なだけ書いてよい。項目数の少なさ自体が品質を保証するわけではない。

**逆に、項目数が少なくても範囲が小さいとは限らない。** 「予約を管理できる」は1項目だが、登録・変更・キャンセル・重複防止まで含む。1つの条件が広すぎる場合は、**実装せず、対象・場面・操作・データのどれを絞れるかを人間に提示する。**

### II. AC1は、端から端まで（NON-NEGOTIABLE）

**AC1 は「これだけ動けば、その人に価値が届く」という、端から端までの流れにする。** 「入力できる」「表示できる」で切らない。

つくるのは「その人がこれをする」という利用の流れ**一本**。分岐、管理画面、設定画面、権限、例外処理の網羅は作らない。

時間が足りないときに削るのは AC2 以降から。**AC1 の「入力から結果まで」の流れは切らない。** 切ると、動いていても解こうとした課題が解けていない状態になる。

ただし、**流れを残したままの簡略化はしてよい。** 対象を一件に絞る、画面を一つにまとめる、外部とのやり取りを模擬する、といった軽くし方である。AC1 が大きすぎると分かった場合は、人間に簡略化案を提示する。**簡略化した内容と模擬した範囲は `spec.md` に記録する。** 機能の数では評価されない。

### III. 75分で動く範囲に収める

開発にかけられるのは合計75分（3限50分＋4限25分）。間に合わないと判断したときは、**機能を足して解決しない。範囲を削る。**

優先順位は AC1 → AC2 → AC3。時間が足りなければ後ろの項目から落とす。落としたことは記録する。

条件を落としたときは、`spec.md`・`plan.md`・`tasks.md` から該当する記述とタスクも削除する。残っていると、消したはずの機能をまた作ってしまう。

### IV. ブラウザだけで動く

成果物は `index.html` を開くだけで動くこと。サーバーの起動、ビルド、パッケージのインストールを必要としない。外部CDNへの依存も原則なしとし、必要な場合は1つまでに限る。

### V. 保存はブラウザの中まで

データの保存が必要な場合は `localStorage` までとする。**外部サービス・データベース・ログイン・決済・通知は作らない。**

それらが必要な設計になった場合は、**動きを模擬（ダミーデータや固定の応答）して進め、模擬した範囲を `spec.md` に書き残す**。模擬した範囲は、成果物テンプレートのスライド10「実現できなかった機能」にも書く。

### VI. 小さく作って、都度動かす

1つのタスクは「画面で動作を目で確認できる単位」まで小さく分ける。大きな変更を一度に行わず、1機能ずつ実装して確認する。

### VII. 日本語で書く

仕様書・計画・タスク・画面の文言は日本語で書く。コード中の識別子は英語でよい。

## 技術的な制約

- 使う技術: HTML / CSS / JavaScript（素のままでよい）
- 対象ブラウザ: 最新の Chrome / Edge / Safari
- テストの自動化は必須としない（受け入れ条件を人が目で確認する）
- ファイル数は必要最小限にする（`index.html` 1ファイルでも構わない）
- 見栄えの作り込みより、AC1〜AC3 が通ることを優先する

## 開発ワークフロー

1. **人間が受け入れ条件（1〜3項目）を決め、絞り込みシート（原本）に書く。スライド8にはその要約を貼る**
2. **シート全文**（確認例と制約を含む）を `/speckit-specify` に渡して仕様書を作り、**人間がレビューして直す**
3. `/speckit-plan` → `/speckit-tasks` で計画とタスクに落とす
4. `/speckit-implement` に**範囲を指定して**、AC1 の実装だけを行う
5. 人が操作して AC1 を確認してから、同じ形で次の条件へ進む

AIが出した仕様・計画・タスクは、人間が承認するまで次の段階に進まない。

**仕様書が受け入れ条件を4項目以上持っていたら、それは誤りである。** 人間が削ってから次へ進む。確認例が複数あることは誤りではない。

実装は一度に全部行わない。**AC1 の実装だけを行い、ブラウザで確認できる状態にして停止する。** 人間の確認を待ってから次の条件へ進む。

## Governance

この憲法は、第7回の目的（決めた解決策を授業時間内に動く形にして確かめる）を優先して定めている。

**この制約は、授業時間内（開発75分）に限ったものである。** 授業後に機能を足す場合は、受け入れ条件を増やしてよい。その際は `spec.md` とこのファイルの記述を一緒に更新し、なぜ変更したのかを記録すること。

授業中は、原則 I・II を変更しない。
