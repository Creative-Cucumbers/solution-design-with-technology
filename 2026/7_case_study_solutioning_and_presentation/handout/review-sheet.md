# 相互確認シート（4限・10分）

第5回の USER TEST を10分に縮めた形です。**他チームと1対1で組みます。**

```
Bチームが、Aチームの試作を操作する（5分）
  ⇄
Aチームが、Bチームの試作を操作する（5分）
```

## 誰が何をするか

役割をはっきり分けます。あいまいなままやると、つくった人が操作して終わってしまいます。

| | やること |
| --- | --- |
| **つくったチーム** | 操作しない。**相手の行動と言葉を観察して、このシートに記録する** |
| **相手のチーム** | 実際に操作する。思ったことは声に出す。分からなければ、分からないと言う |

**記録を書くのは、つくったチーム自身です。** 自分たちの試作に対する反応を、自分たちの目で見てください。終わったあと、シートは手元に残します。

---

## 見せる側のルール

### ASK, DON'T SELL（売り込まず、聞く）

第5回でやったとおりです。説明しすぎず、相手の反応を待ちます。

| | NG | OK |
| --- | --- | --- |
| 聞き方 | 「便利ですよね？」 | 「この画面を見て、まず何をすると思いますか？」 |
| 態度 | 使い方を先回りして教える | 相手が迷ったら、その様子を黙って見る |
| 反応 | 「そこは違います」 | 「いま、何を探していましたか？」 |

### 渡すのは「達成したい仕事」だけ

**受け入れ条件や操作手順は言わないでください。** 何をすればよいか相手が分からないなら、それ自体が分かったことです。

```
この人は（ペルソナを一言で）＿＿＿＿＿＿＿＿です。
この人は、いま（達成したい仕事）＿＿＿＿＿＿＿＿をしようとしています。
やってみてください。
```

### 確かめることは2つある。混同しない

第5回の区別をそのまま使います。

| | 問い | 分かること |
| --- | --- | --- |
| **① Solution Hypothesis** | このSolutionでいい？ | 課題に合っているか、この人の役に立ちそうか |
| **② Concept / Prototype** | このつくり方で伝わる？ | 何をするものか分かるか、操作が伝わるか |

**操作できなかった＝価値がない、ではありません。** 表現や操作の問題かもしれません。どちらの話なのかを分けて記録してください。

## 記録シート（つくったチームが書く）

**自分たちのチーム名：＿＿＿＿＿＿　操作してもらったチーム：＿＿＿＿＿＿　書いた人：＿＿＿＿＿＿**

### 1. 渡す前に決める（1分）

```
渡す「達成したい仕事」：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿
こう操作するはず（自分たちの予想）：＿＿＿＿＿＿＿＿＿＿
```

### 2. 見たことを書く（3分）

> [!IMPORTANT]
> **ここには、見たこと・聞いたことだけを書きます。** 解釈や「直すべきこと」は、次の3に書きます。混ぜないでください。

第5回で習った、注目すべき反応です。

> 迷う。止まる。誤解する。期待と違う行動をする。良いと言うが、使わない。思わぬ使い方をする。

```
やっていたこと（行動。見えたままを書く）：


言っていたこと（そのままの言葉で）：


どこで止まった・迷ったか：
```

### 3. 自分たちの解釈を書く（1分）

```
なぜそうなったと考えるか：


それは ① Solution の話か、② つくり方の話か：
  □ ① 課題に合っていない／この人の役に立たなそう
  □ ② つくり方・見せ方が伝わらない
  □ 判断できない
```

### 4. 判断する（KEEP / CHANGE / QUESTION）

| | 意味 | 書くこと |
| --- | --- | --- |
| **KEEP** | 残す | 伝わっていた、役に立ちそうだったところ |
| **CHANGE** | 変える | 変えたほうがよさそうなところと、そう思った理由 |
| **QUESTION** | まだ分からない | 今回では判断できなかったこと。空欄にせず残す |

```
KEEP     ：

CHANGE   ：
  理由   ：

QUESTION ：
```

> [!NOTE]
> **2は観察した事実ですが、3と4は自分たちの判断です。** 「確かめられた事実」として扱わないでください。
>
> 相手が言う「これ、便利ですね」「現場では使えないと思います」は、**需要や業務への適合についての意見**です。操作した学生は、その仕事の当事者ではありません。**実ユーザーによる検証の結果ではなく、確かめるべき仮説として** QUESTION に書いてください。

## 7節（10分）でやること

> [!IMPORTANT]
> **Feedback を、そのまま修正リストにしないでください。** 第5回でやったとおりです。

### 対応を決める（3分）

1. CHANGE を読み、**なぜそう言われたのか**を考える
2. **直すもの**と、**直さないもの**に分ける
3. 直さないものは、**理由と、次にどう確かめるか**を書く

全部直す必要はありません。**直せる数は1つか2つ**だと思ってください。

```
直す：
  変更内容：
直さない：
  理由：
  次にどう確かめるか：
```

### 直して、もう一度確かめる（7分）

直したら、**同じ操作をもう一度やって**、意図どおりになったかを見ます。直しっぱなしにしないでください。

```
いまの変更で、現在の spec.md で採用している受け入れ条件がまだ通るかを
確認したいです。修正はしないでください。

それぞれについて、通るか通らないかと、確認した操作を1行で書いてください。
実際に操作して確認できないものは「未確認」と記録してください。
```

最後の2分は触らず、デモの通し確認に使ってください。
