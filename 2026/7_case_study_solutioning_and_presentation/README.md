**今日の問い：課題を見つけて、解いて、届ける。その一本を、自分たちで通しきれるか？**

世の中の問題を見つける。その課題を解く。そして、人が使える形にして届ける。**この一連が通って、はじめてソリューションです。** どれかひとつが欠けていると、良いアイデアも、よくできた資料も、誰の仕事も変えません。第1回から第6回まで、この流れを分けて学んできました。今日はその最後の区間です。

**速くつくるのは、目的ではなく手段です。** 今日は開発に75分しか使えません。けれどこれは速さを競うという意味ではありません。早く形にするのは、**早く確かめるため**です。頭の中にあるうちは、どんなアイデアも良く見えます。触れる形にして初めて、思っていたのと違うところが見えます。

**要件と設計を先に押さえるのも、作業を速くするためではありません。** 第2回の受け入れ条件、第4回のアーキテクチャ図。これらは、**何を確かめたのかが分かる形にして、アイデアを進化させ続けるため**にあります。決めずにつくったものは、動いても何が効いたのか分かりません。次に何を変えればいいかも分かりません。それは、学んだことを次に引き継げない試作です。

だから今日は、全部つくろうとせず、**確かめたいことが分かる最小の形**をつくります。絞ることは妥協ではありません。**何を捨てたかを説明できることが、今日の成果物の一部です。**

### 1.5 進め方を決める（5分）

今日は**作業を分けません。1台の画面を、チーム全員で見ながら進めます。**

第4回の4限は、各自が案を比較して持ち寄り、チームで一つに決めて図にし、検証する形でやりました。今日は目的が違います。**つくるのは受け入れ条件1〜3項目ぶん**なので、分けて合流する手間のほうが大きくなります。それに、AIが手を動かしてくれる今、詰まるのは**打つ速さではなく、判断**です。操作している人は目の前の作業に集中するので、**別の視点から目的・範囲・確認漏れを点検する人**がいると、気づくのが早くなります。

#### 役割は2つだけ

| 役割 | やること |
| --- | --- |
| **操作する人** | AIに指示を出し、画面を動かす。考えていることを**声に出しながら**やる |
| **見ている人** | 画面を見て、気づいたことをその場で言う。**絞り込みシートを手元に開いておく** |

2人のチームは、この2役です。これを **ペアプログラミング（ペアプロ）** と呼びます。3人のチームは、見ている人が2人になります。こちらは **モブプログラミング（モブプロ）** と呼ばれます。授業では呼び方はどうでもよく、**全員が同じ画面を見ていること**が大事です。

> [!IMPORTANT]
> **黙って見ないでください。** 見ている人が何も言わないなら、1人でやっているのと同じです。分からないことがあったら、その場で聞いてください。「いま何をしているの？」と聞くのは、じゃまではなく仕事です。

#### 見ている人の、いちばん大事な仕事

**「それ、AC1〜AC3に入ってる？」と聞くことです。**

今日いちばん起きやすい失敗は、つくっているうちに範囲が膨らむことです。操作している人は目の前の作業に集中するので、気づきにくくなります。**見ている人は、目的・範囲・確認漏れを別の視点から点検する役**です。絞り込みシートを手元に開いたまま、入っていないものが出てきたら、その場で声に出してください。

#### 交代する

**10分ごと、または AC が1つ通ったら交代**してください。ずっと同じ人が操作していると、その人しか中身を説明できなくなります。

最終発表では、**つくった人以外も説明できる**ことが求められます。個人の提出物でも「自分が判断したことと、その根拠」を書きます。交代は、そのための時間でもあります。

#### PCと、資料の扱い

- **操作に使うPCは1台で十分です。** 残りのPCは、資料（成果物テンプレート8〜11）や調べものに使ってください
- **資料係を置かないでください。** スライドを埋める時間は、2節・3節・8節に別に取ってあります。そこで全員で書きます
- 3人チームは、見ている人のうち1人が**確認結果を書き留める**と、あとの作業が楽になります

## 2. 受け入れ条件を絞り、仕様書にする (20分)

### 2.1 今日いちばん重要な20分です

絞るのは、時間が足りないからだけではありません。**何を確かめたいのかを、先に決めるためです。**

内訳は、**考える8分 → 受け入れ条件に整理する7分 → 仕様書をつくって確かめる5分**です。

全部つくって動いたとしても、何が効いて何が外れたのかは分かりません。条件を決めてからつくれば、動かしたときに「AC1は通った、AC2は思っていたのと違った」と言えます。**次に何を変えればいいかが、手元に残ります。** それがアイデアを進化させる元手になります。

そのうえで、現実の制約もあります。第6回で出した解決策は、たいてい**75分では終わりません**。ここで絞らないと、どこも動かないまま発表を迎えます。

やることは一つです。[絞り込みシート](./handout/scope-and-spec.md)を埋めます。**いきなり受け入れ条件を書くのではなく、「何を確かめたいか」から考えます。**

```
絞り込みシート ──→ 要約を成果物テンプレート8「要件定義」に貼る
      │
      └──→ 確認例と制約を含むシート全文を /speckit-specify に貼る ──→ spec.md → plan.md → 実装
```

**シートが源で、`spec.md` はそこから派生したものです。** 順番を逆にしないでください。先に Spec Kit を回すと、AIが気を利かせて要件を増やし、75分では終わらない仕様書ができあがります。

### 2.2 まず「確かめたいこと」から考える（8分）

いきなり受け入れ条件を書き始めないでください。**まず自分たちの言葉で考えて、そのあとで条件の形に整えます。**

```
【前半】考える欄   ①〜⑥を順に埋める（チームで判断・必要に応じてAIに相談／8分）
                        ↓  AIに整理してもらう
【後半】渡す欄     受け入れ条件の形に整え、人間が確認する（7分）
                        ↓
            要約を成果物テンプレート8へ ／ 全文を /speckit-specify へ
```

> [!IMPORTANT]
> **項目数を3つにしても、つくる範囲が小さくなるとは限りません。** 「予約を管理できる」は1項目ですが、登録・変更・キャンセル・重複防止まで含みます。数だけでなく、**対象・場面・操作・データの広がり**を絞る必要があります。①〜⑥は、そのための欄です。

[絞り込みシート](./handout/scope-and-spec.md)の前半を、この順に埋めます。**まずチームで考えてください。** 言葉にできない、選択肢が浮かばないときは、AIに相談してかまいません（2.6節）。ただし、**採用する内容と理由はチームで決めてください。**

| | 問い | ホテルの例 |
| --- | --- | --- |
| **① 今回確かめたいこと** | この試作で、何が分かれば一歩前に進む？ | フロントが、電話せずに清掃状況を読み取れるか |
| **② 今回扱う場面** | 誰が、いつ、何をする場面だけをつくる？ | 清掃担当が完了を記録し、フロントが確認する場面 |
| **③ 最後にできてほしいこと** | 操作が終わったとき、何が分かる・できる？ | どの部屋が清掃済みか分かる |
| **④ 小さくする方法** | 人・画面・データ・処理を、どう減らす？ | ホテル一つ、部屋三つ、同じPCで担当を切り替える |
| **⑤ 今回の線引き** | 実際につくる／代わりの方法で試す／今回は扱わない、のどれ？ | 状態変更はつくる。別端末の共有は代用。予約連携は扱わない |
| **⑥ 合格の確かめ方** | 何を操作して、どうなれば予定どおり？ | 502号室を完了にすると、一覧の502号室だけが変わる |

### 2.3 削るかどうかは、この問いで決める

④と⑤で迷ったら、一つずつこう聞いてください。

> **それを今回つくらなくても、①で書いた「確かめたいこと」は確かめられる？**

| 答え | どうするか |
| --- | --- |
| **はい** | 後回し、または模擬の候補。⑤で「代わりの方法で試す」か「今回は扱わない」へ |
| **いいえ** | 残す。または、もっと簡単な方法に置き換えられないか考える |

ホテルの例なら、**通知がなくても**画面を切り替えて清掃状態の読み取りは試せます。一方、**清掃状態そのものが表示されなければ**、確かめたいことが確かめられません。この違いが、残すか削るかの境目です。

**模擬にしたものには、それによって確かめられなくなることを添えてください。**

> 同じPCで担当を切り替える試作なら、**表示の読み取りやすさは確かめられます**。
> けれど、**実際の端末間での共有や、繁忙時の入力の手間までは確かめられません。**

ここに書いたことは、成果物テンプレート11の QUESTION になります。

### 2.4 受け入れ条件に整理する（7分）

前半が埋まったら、AIに受け入れ条件の形へ整理してもらい、**人間が確認します。**

下の完全版プロンプトは[絞り込みシート](./handout/scope-and-spec.md)の「後半：渡す欄」にあります。**条件と出力のひな形を含めてあるので、後半の下書きまでAIが作ります。転記は要りません。**

```
上で決めた①〜⑥を、実装する範囲と受け入れ条件に整理してください。
私たちが確認するまで実装しないでください。

【条件】
- 受け入れ条件は1〜3項目にまとめる。機能は追加しない
- AC1は「入力から結果まで」の一連の流れが通る条件にする。
  「入力できる」「表示できる」で切らない
- 1つの条件に、確認例を2〜3個添えてよい
- ブラウザだけで動く。保存は localStorage まで。外部サービス・DBは使わない
- まだ広すぎる箇所があれば、小さくする案を添える

【私たちが決めたこと】
① 確かめたいこと：
② 扱う場面：
③ 最後にできてほしいこと：
④ 小さくする方法：
⑤ 線引き：
⑥ 合格の確かめ方：

【出力の形式】下の形のまま、埋めて返してください。

今回確かめたいこと：
主要な利用の流れ：＿＿＿が、＿＿＿して、＿＿＿できる

AC1  （端から端まで）
     確認1：
     確認2：
AC2
     確認：
AC3  （余力があれば）
     確認：

今回つくらないもの：
模擬する範囲：
  模擬したことで確かめられなくなること：
制約：ブラウザだけで動く／保存は localStorage まで／外部サービス・DBは作らない

この人が使い続けるうえで、いちばん気になる障害は：
今回の試作で確かめられるのはどこまでで、実ユーザーに確かめたいのは：
```

出てきたものを**そのまま採用しないでください。** 次の3点を確かめます。

- 自分たちが決めていない機能が増えていないか
- 小さくしても、①で書いた「確かめたいこと」が残っているか
- 模擬した範囲と、それによって確かめられないことが、正しく書かれているか

合わない箇所は自分たちで直します。次のルールが判断の基準です。

| | |
| --- | --- |
| **受け入れ条件は1〜3項目** | 主要な流れを成立させる条件にまとめる。4項目目を足したくなったら「今回つくらないもの」へ送る |
| **AC1は、端から端まで** | **AC1だけでも、その人に価値が届く流れが通ること。**「入力できる」「表示できる」で切らない |
| **主要な流れは一本** | 分岐、管理画面、設定、権限、例外処理の網羅はつくらない |
| **確認例は複数付けてよい** | 1つの条件に確認を2〜3個書いてかまいません。**正しく動くことを確かめる例（同じ操作を2回する、別の対象に誤って反映しないか）は、条件を増やすことではありません** |
| **間に合わないときは削る** | 機能を足して解決しない。後ろの項目から落とす |

> [!IMPORTANT]
> **AC1の切り方がいちばん大事です。** 「清掃完了を押せる」で止めると、AC2を落としたときにフロントへ何も届かず、解こうとした課題が解けません。**AC1だけ残しても、その人の仕事が少しよくなる**ところまでを1項目にしてください。

整理できたら、シートの後半（渡す欄）に書きます。記入例です。

```
今回確かめたいこと：フロントが、電話せずに清掃状況を読み取れるか
主要な利用の流れ：清掃担当が完了を記録すると、フロントが入れる部屋を把握できる

AC1  清掃担当が502号室の清掃完了を記録すると、
     フロント用の一覧で502号室が「清掃済み」と分かる
     確認1：未清掃の502号室を完了に変え、フロント表示に切り替えて、
            番号と状態が一致することを確認する
     確認2：同じ部屋を続けて2回完了にしても、一覧の行は1つのまま
AC2  フロントが「いま入れる部屋」だけに絞って表示できる
     確認：絞り込むと、清掃済みの部屋だけが並ぶ
AC3  （余力があれば）清掃済みになった時刻が分かる
     確認：完了を押した部屋に、押した時刻が表示される

今回つくらないもの：ログイン／複数ホテル対応／通知／清掃履歴の蓄積／予約連携
模擬する範囲：清掃担当とフロントは、同じページ内で表示を切り替えて代用する
  模擬したことで確かめられなくなること：
    実際の端末間での共有と、繁忙時の入力の手間
制約：ブラウザだけで動く／保存は localStorage まで／外部サービス・DBは作らない

この人が使い続けるうえで、いちばん気になる障害は：
  清掃担当の入力の手間が増えすぎないか。古い状態を信じて案内してしまわないか
今回の試作で確かめられるのはどこまでで、実ユーザーに確かめたいのは：
  画面の分かりやすさまでは今日確かめられる。
  繁忙時に本当に入力してもらえるかは、実際のフロントに聞くまで分からない
```

AC1 だけが通った状態でも、「清掃が終わったことがフロントに伝わる」という価値は届きます。AC2・AC3 はそこへの追加です。**この切り方にしておくと、時間が足りなくなっても課題を解く流れが残ります。**

> [!IMPORTANT]
> **チームが合意した絞り込みシートが原本です。成果物テンプレート8は、その要約です。**
> Spec Kit に渡すのは、**確認例と制約を含むシート全文**です。スライドに書いた要約を渡さないでください。詳細が落ちた仕様書になります。
>
> 評価は、成果物テンプレート8・シート・`spec.md` を合わせて見ます。

> [!IMPORTANT]
> **「今回つくらないもの」が空のチームは、まだ絞れていません。** 第6回で出したアイデアのうち、今日やらないことを必ず書いてください。ここに書いたものは減点ではなく、**判断した記録**として評価されます。

### 2.5 使い続けられるかを、一つだけ考える

第6回で「一時的な便利さだけでなく、実際の仕事の流れに合い、継続して価値を届けられるか」を考えました。今日の75分でそれを証明することはできません。**確かめるべき仮説として残す**のが到達点です。

シートの最後の2行がそれにあたります。ここに書いたことは、**成果物テンプレート11の QUESTION** と、最終発表の⑤になります。

### 2.6 考えが進まないときに相談する

①〜⑥を考える途中で、言葉にできない・選択肢が浮かばないときに使います。**答えをもらうためではなく、候補を広げるため**です。出てきたものを**そのまま採用しないでください**。自分たちのペルソナと課題に照らして判断するのはチームです。

```
これから、試作の範囲を決めます。実装はまだしないでください。

【対象】（成果物テンプレート5のペルソナを貼る）
【解決したい課題】（成果物テンプレート6を貼る）
【考えている解決策】（成果物テンプレート7を貼る）

開発にかけられるのは合計75分、2〜3人のチーム、ブラウザだけで動くものです。

次の3つについて、候補を出してください。

1. この試作で「何が分かれば一歩前に進む」と言えますか。候補を3つ
2. そのために最低限つくる必要がある場面は、どれですか
3. 人・画面・データ・処理を減らす方法を、それぞれ挙げてください

機能の一覧ではなく、「何を確かめたいか」から答えてください。
```

### 2.7 仕様書をつくって確かめる（5分）

シートが埋まったら、まず**要約を成果物テンプレート8に貼ります**。Spec Kit に渡すのは、**シート全文**です（確認例と制約を含みます）。

スターターは第7回用のものを使ってください。第2回のものとは `constitution.md`（プロジェクトの憲法）が違います。

- Windows → **[starter-windows.zip](https://raw.githubusercontent.com/Creative-Cucumbers/solution-design-with-technology/main/2026/7_case_study_solutioning_and_presentation/starter-windows.zip)**
- Mac / Linux → **[starter-mac.zip](https://raw.githubusercontent.com/Creative-Cucumbers/solution-design-with-technology/main/2026/7_case_study_solutioning_and_presentation/starter-mac.zip)**

展開してできたフォルダ**そのもの**を Antigravity IDE で開きます。チャットで `/speckit-` と打ってコマンド一覧が出れば準備完了です。

```
/speckit-specify 以下の受け入れ条件だけを満たすアプリをつくります。

（ここに絞り込みシートを丸ごと貼る）

受け入れ条件は上に書いたものだけです。項目を増やさないでください。
良さそうに見える機能も足さないでください。
各条件に書いた確認例は、そのまま仕様書に残してください。
足したほうがよいと思うものがあれば、実装せず、提案だけ最後に書いてください。
```

できた `spec.md` は**必ず読んでください**。見るのは4点です。

- 受け入れ条件の項目数が、自分たちが書いたままか（増えていたら削る）
- **AC1が、端から端まで通る条件のままか**
- 「今回つくらないもの」に書いたものが混ざっていないか
- 確認例が、自分たちが書いたとおりか

> [!NOTE]
> 第7回のスターターの `constitution.md` には「受け入れ条件は1〜3項目」「AC1は端から端まで（流れを残した簡略化は可）」「絞り込みシートが原本」「75分で動く範囲に収める」と書いてあります。AIはこれに従います。それでも増えることはあるので、**自分の目で確認してください。**

## 3. 構成を決めて、技術を選ぶ (12分)

第4回でやったことを、自分たちのテーマでやります。**成果物テンプレート9**を埋めます。
内訳は、**比較・選択5分 → 作図・説明の確認5分 → 理由の記録2分**です。

### 3.1 2案だけ比べて、1案を選ぶ（5分）

比較・選択に使えるのは5分です。**中身がはっきり違う2案**を比べます。

```
構成を考えます。実装はまだしないでください。

spec.md の受け入れ条件を満たす構成を、中身がはっきり違う2案だけ出してください。
似た案を2つ並べないでください。

それぞれについて、次を表で比べられる形にしてください。

- どんな部品に分けるか（部品の名前と、その部品がやること・やらないこと）
- データをどこに、どんな形で持つか
- AC1の操作から表示まで、情報がどう流れるか

あわせて、各案について次を1行ずつ書いてください。
- この人の仕事の進め方に合っているか
- この人の手間が増えないか
- 2〜3人が残り50分でつくれるか
```

選ぶときに見るのは、**その人の仕事に合うか**、**残り時間でつくれるか**、**全員が説明できるか**の3つです。きれいな設計より、通る設計を選んでください。

### 3.2 図をAIに描かせて、自分たちで確かめる（5分）

白紙から描くと時間が足りません。**AIに下書きを描かせて、自分たちが直します。**

```
選んだ案を、draw.io で開ける図にしてください。実装はまだしないでください。

- 主要な部品は3〜5個までにしてください
- 部品の名前は、専門用語を使わず、やさしい日本語にしてください
- 矢印は「何を渡すか」と「何が返るか」が分かるように、言葉を添えてください
- あとから編集できる形（.drawio または .drawio.svg）で出力してください
```

できた図で、**AC1の操作を1件、指でたどってください。** 「502号室の完了を押す」から「フロントの一覧が変わる」まで、矢印を順に追えますか。追えない箇所があれば、そこが設計の穴です。

> [!IMPORTANT]
> **描いた人以外が、その図で説明できるか**を確かめてください。説明できない線があったら、AIに聞いて言い換え、自分たちの言葉に直します。第4回でやった「仕上げの3点」と同じです。

図とこの選択理由は保存し、次の `/speckit-plan` で参照先として渡します。

```
例：清掃完了が、フロントの画面に届くまで

  [清掃担当の画面] --(部屋番号と「完了」)--> [部屋の状態を持つところ]
                                                      |
                                              (状態が変わる)
                                                      ↓
                                            [フロントの一覧画面]
```

### 3.3 技術選択の理由を書く（2分）

**成果物テンプレート9**に、この3行を書きます。評価観点5にそのまま対応します。

```
選んだ技術：
選んだ理由：
捨てたもの（と、捨てた理由）：
```

「AIが選んだから」は理由になりません。**なぜそれが、自分たちの3条件に合うのか**を書いてください。

## 4. つくって、確かめる (50分)

1台の画面を全員で見ながら進めます（1.5節）。**10分ごと、またはACが1つ通ったら交代**してください。

### 4.1 計画とタスクに落とす

```
/speckit-plan 選んだ構成に従って設計してください。

部品の分け方・データの持ち方・情報の流れは、私たちが決めた構成のとおりにしてください。
図は（ファイル名）に保存してあります。そちらを正としてください。
勝手に変えないでください。変えたほうがよい場合は、理由を書いて提案だけしてください。

受け入れ条件は spec.md に書いたものだけです。それ以外は実装しないでください。
```

出てきた `plan.md` は**読みます**。第4回と同じく、見るのは「決めたつなぎ目がそのまま使われているか」「勝手に足された前提がないか」です。

```
/speckit-tasks
```

### 4.2 AC1から順に、一つずつ動かす

`/speckit-implement` を引数なしで打つと、**タスク全体を一気に実装します。** それでは途中で確認できません。**最初から範囲を指定して呼びます。**

```
/speckit-implement AC1を満たすための共通準備と実装だけを行ってください。
AC2・AC3固有の実装には進まないでください。
AC1をブラウザで確認できる状態にしたら停止し、
確認手順を示して、私たちの確認を待ってください。
```

AC1 が通ったことを**自分の手で確認してから**、同じ形で AC2 に進みます。確認は、絞り込みシートに書いた「確認」のとおりにやってください。

```
/speckit-implement 次はAC2の実装だけを行ってください。
AC1がこれまでどおり通ることも確認できる状態にして、停止してください。
```

### 4.3 30分たったら、膨らんでいないか見る

30分くらい経つと、たいてい膨らんでいます。一度止めて確認してください。

```
いまのコードを確認して、報告だけしてください。コードは変更しないでください。

1. spec.md の受け入れ条件に書かれていない機能が入っていませんか。あれば一覧にしてください
2. それぞれ、消した場合に受け入れ条件のどれかが壊れますか
3. 壊れないものについて、消す提案をしてください（実行はしないでください）
```

### 4.4 動かなくなったとき

```
いま動かない箇所を切り分けたいです。修正はまだしないでください。

現在の spec.md で採用している受け入れ条件のそれぞれについて、
いま通るか通らないかを判定してください。
実際に操作して確認できないものは「未確認」と記録してください。
通らないものは、どの操作のどこで止まるのかを1行で書いてください。

そのうえで、直す順番を提案してください。AC1 が通らないなら、それが最優先です。
```

### 4.5 間に合わないと分かったら、範囲を削る

**最後まで粘って何も動かないのが、一番よくありません。** 気づいた時点で削ってください。

| 残り時間 | やること |
| --- | --- |
| 残り20分で AC1 も通っていない | AC2 以降を捨てる。**AC1 が端から端まで通ることを最優先**します |
| AC1 は通った、AC2 が重い | AC2 の中身を軽くする。データを固定値にする、画面を1つにまとめる |
| AC1・AC2 は通った | AC3 に進む。間に合わなければ成果物テンプレート10に「未実装」と書く |

> [!IMPORTANT]
> **AC1の「入力から結果まで」の流れは切らないでください。** ここを切ると、動いていても課題が解けていない状態になります。削るのは AC2 以降からです。
>
> ただし、**流れを残したままの簡略化はしてかまいません。** 対象を一件に絞る、画面を一つにまとめる、外部とのやり取りを模擬する、といった軽くし方です。AC1 が大きすぎたと分かったときは、こちらで調整してください。**簡略化した内容と模擬した範囲は記録します**（成果物テンプレート8と10）。

条件を減らしたら、**シート・`spec.md`・`plan.md`・`tasks.md` を揃えてください。** 揃っていないと、AIが消したはずの機能をまた作ります。

```
受け入れ条件からAC3を外しました。実装はまだしないでください。
spec.md・plan.md・tasks.md から、AC3に関する記述とタスクを削除する案を出してください。
AC1・AC2に必要なものを巻き込んでいないかも確認してください。
```

削ったことは**隠さずに書いてください**。成果物テンプレート10「実現できなかった機能」に、何を落としたか、なぜ落としたかを書きます。**判断した記録として評価されます。**

> **予備の8分について。** 2節で絞りきれなかったチーム、仕様書の確認が終わらなかったチームは、ここを使ってください。**開発を延ばすより、戻って絞り直すほうが効果があります。**

| # | 内容 | 時間 | 形式 |
| --- | --- | --- | --- |
| 5 | 実装の仕上げと動作確認 | 15分 | チーム |
| 6 | 他チームと確かめる | 10分 | 2チームで1組 |
| 7 | 対応を決めて直し、再確認する | 10分 | チーム |
| 8 | 最終発表の準備 | 15分 | チーム |
| 9 | 最終発表・質疑 | 35分 | 全体 |
| 10 | 個人の振り返り | 5分 | 個人 |
| | 予備 | 10分 | |
| | **合計** | **100分** | |

開発に使える時間は、3限の50分とここの15分＋10分で、合わせて75分です。**6節で他チームに確かめてもらい、7節でその結果を踏まえて直します。** つくって終わりにせず、確かめて直すところまでを一周します。

## 5. 実装の仕上げと動作確認 (15分)

3限と同じく、1台の画面を全員で見ながら進めます。**機能を増やす時間ではありません。** やることは2つだけです。

1. **AC1〜AC3 のうち、通っていないものを通す**
2. **他チームに触ってもらえる状態にする**（どこから始めればよいかが分かること）

新しい機能を思いついても、ここでは足しません。成果物テンプレート11の QUESTION に書いて、次へ持ち越してください。

次の10分で、他チームが実際に操作します。**初期データを入れておく**など、触り始められる状態にしてから6節に進んでください。

## 6. 他チームと確かめる (10分)

第5回の **USER TEST** を10分に縮めた形です。**他チームと1対1で組みます。**

```
Bチームが、Aチームの試作を操作する（5分）
  ⇄
Aチームが、Bチームの試作を操作する（5分）
```

### 6.1 誰が何をするか

役割をはっきり分けます。あいまいなままやると、つくった人が操作して終わってしまいます。

| | やること |
| --- | --- |
| **つくったチーム** | 操作しない。**相手の行動と言葉を観察して、[相互確認シート](./handout/review-sheet.md)に記録する** |
| **相手のチーム** | 実際に操作する。思ったことは声に出す。分からなければ、分からないと言う |

**記録を書くのは、つくったチーム自身です。** 自分たちの試作に対する反応を、自分たちの目で見てください。

### 6.2 見せる側 ── ASK, DON'T SELL

第5回でやったとおり、売り込まず、聞きます。

| | NG | OK |
| --- | --- | --- |
| 聞き方 | 「便利ですよね？」 | 「この画面を見て、まず何をすると思いますか？」 |
| 態度 | 使い方を先回りして教える | 相手が迷ったら、その様子を黙って見る |
| 反応 | 「そこは違います」 | 「いま、何を探していましたか？」 |

最初に渡すのは、**達成したい仕事**だけです。受け入れ条件や操作手順は言わないでください。何をすればよいか相手が分からないなら、それ自体が分かったことです。

```
この人は（ペルソナを一言で）＿＿＿＿＿＿＿＿です。
この人は、いま（達成したい仕事）＿＿＿＿＿＿＿＿をしようとしています。
やってみてください。
```

### 6.3 確かめることは2つある。混同しない

第5回の区別をそのまま使います。

| | 問い | 分かること |
| --- | --- | --- |
| **① Solution Hypothesis** | このSolutionでいい？ | 課題に合っているか、この人の役に立ちそうか |
| **② Concept / Prototype** | このつくり方で伝わる？ | 何をするものか分かるか、操作が伝わるか |

> [!IMPORTANT]
> **操作できなかった＝価値がない、ではありません。** 表現や操作の問題かもしれません。どちらの話なのかを分けて記録してください。

### 6.4 見たことと、考えたことを分けて書く

ここが今日いちばん間違えやすいところです。**3段階に分けて、この順で書いてください。**

| 順 | 書くこと | 例 |
| --- | --- | --- |
| 1 | **見た行動・聞いた言葉**（事実） | 一覧を上から順に目で追っていた。「絞り込みってどこですか」と言った |
| 2 | **その解釈**（自分たちの読み） | 絞り込みボタンに気づいていないのではないか |
| 3 | **KEEP / CHANGE / QUESTION**（判断） | CHANGE：ボタンを一覧の上に移す |

1は観察した事実ですが、**2と3は自分たちの判断です。** 「確かめられた事実」として扱わないでください。

第5回で習った、注目すべき反応です。

> 迷う。止まる。誤解する。期待と違う行動をする。良いと言うが、使わない。思わぬ使い方をする。

> [!NOTE]
> 相手が言う「これ、便利ですね」「現場では使えないと思います」は、**需要や業務への適合についての意見**です。操作した学生は、その仕事の当事者ではありません。**実ユーザーによる検証の結果ではなく、確かめるべき仮説として** QUESTION に書いてください。

## 7. 対応を決めて直し、再確認する (10分)

**Feedback を、そのまま修正リストにしないでください。** 第5回でやったとおりです。

### 7.1 対応を決める（3分）

1. 記録した CHANGE を読み、**なぜそう言われたのか**を考える
2. **直すもの**と、**直さないもの**に分ける
3. 直さないものは、**理由と、次にどう確かめるか**を書く

全部直す必要はありません。残り時間は7分です。**直せる数は1つか2つ**だと思ってください。

### 7.2 直して、もう一度確かめる（7分）

直したら、**同じ操作をもう一度やって**、意図どおりになったかを見ます。直しっぱなしにしないでください。

```
いまの変更で、現在の spec.md で採用している受け入れ条件がまだ通るかを
確認したいです。修正はしないでください。

それぞれについて、通るか通らないかと、確認した操作を1行で書いてください。
実際に操作して確認できないものは「未確認」と記録してください。
```

> [!WARNING]
> **発表の直前に大きな変更をしないでください。** 動いていたものが動かなくなると、デモができません。10分のうち、最後の2分は触らずに通し確認に使ってください。

直した内容と、直さないと決めた内容は、どちらも成果物テンプレート11に残します。

# 課題と評価

## 提出物

Slackの第7回提出用スレッドへ、**授業終了後3日以内**に投稿してください。

| 提出単位 | 提出物 | 評価すること |
| --- | --- | --- |
| **チーム** | 成果物テンプレートの成果物テンプレート1〜11（PDFまたは共有リンク） | 対象・課題・解決策・実装・確認が一本につながっているか（観点3） |
| **チーム** | 成果物テンプレート8と絞り込みシート（受け入れ条件、つくらないもの、模擬する範囲） | 範囲を絞り、何を捨てたかを説明できるか。**AC1が端から端まで通る形か**（観点4） |
| **チーム** | 成果物テンプレート9（構成図と技術選択の理由） | 部品・責務・情報の流れを説明でき、選択の理由を言えるか（観点1・5） |
| **チーム** | **プロジェクト一式をまとめたZIPの共有リンク**（ソース、`specs/` 配下の `spec.md` / `plan.md` / `tasks.md`、起動手順を書いた `README.txt`、初期データ） | 仕様・計画・実装が対応しているか。**他の人が同じ手順で動かせるか**（観点4） |
| **チーム** | 成果物テンプレート11（KEEP / CHANGE / QUESTION） | 確かめた範囲と、まだ分からない範囲を区別できるか（観点3） |
| **全員個別** | 10節の3点を、自分の言葉で | 自分の判断を説明できるか（観点2・4） |

> [!IMPORTANT]
> **他の人が開いて動かせる形で出してください。** 自分のPCでしか動かないと、評価できません。ZIPには「どのファイルを開けばよいか」「最初に何を入れればよいか」を書いた `README.txt` を1枚入れてください。
>
> 生成AIとのやりとりは、共有URLが作れるサービスなら**リンク**を、作れない場合は**判断に関わった部分の抜粋をテキストで**出してください。全部のログは要りません。

AIが生成したコードや文章をそのまま出すだけでは、自分の理解は確認できません。**採用した理由と、確認したことを自分の言葉で書いてください。**

## 到達の目安

- **つながっている**：課題 → 解決策 → 動くもの → 確かめたこと、が一本の筋で説明できる。どこかが切れていたら、動いていても届いていません。
- **通っている**：主要な利用の流れが一本、最後まで動く。**AC1 が端から端まで通っていれば、動作面はそれで足ります。**
- **説明できる**：構成図を使って、情報がどう流れるかを説明できる。なぜその技術を選んだかを言える。
- **区別できている**：観察した行動・言葉、その解釈、KEEP / CHANGE という判断、未確認の QUESTION が、混ざらずに分かれている。落とした機能とその理由が書いてある。
- **次がある**：つくって分かったことから、次に何を変えるかが言える。

> [!NOTE]
> **「AC1が通れば足りる」のは、動作面の最低到達条件です。** それだけで全体の評価が決まるわけではありません。上の5つは、根拠・説明・確認も含めてまとめて見ます。
>
> 逆に、AC1〜AC3 がすべて通っていても、課題とのつながりが説明できなかったり、確かめたことと確かめていないことが分かれていなければ、届いたとは言えません。

**機能の数、画面の見栄え、AIの利用量では評価しません。** 落とした機能が多いことも減点ではありません。判断の理由が書いてあるかを見ます。**速くつくれたことも評価しません。** 速さは、早く確かめるための手段です。

## 事後学習

- **未実装の範囲を1つ進める、または既存を確かめ直す（3時間程度）**：次のどちらかを選んでください。
  - 成果物テンプレート10に「実現できなかった」と書いたもののうち1つを選び、**受け入れ条件を1つ書き足して**実装する。何が難しかったかを記録する。
  - 新しい機能は足さず、AC1〜AC3 の**確認例を増やして**確かめ直す。崩れた箇所と、直した内容を記録する。

> [!NOTE]
> **「受け入れ条件は1〜3項目」は、授業中の75分に限った制約です。** 事後学習で条件を足すのはかまいません。足すときは、`spec.md` と `.specify/memory/constitution.md` の記述も一緒に更新してください。制約を変えたなら、変えたことを書き残すのがルールです。
- **QUESTION を1つ確かめる（2時間程度）**：成果物テンプレート11に残した QUESTION のうち1つを選び、どうすれば確かめられるかを設計する（誰に、何を聞くか／何を観察するか）。実施は必須ではありません。

## この演習のおわりに

7回を通して、次の一周を自分たちの手で回しました。

```
ユーザーを知る → 課題を定める → 解決策を選ぶ → 設計する → つくる → 確かめる → 更新する
```

**一度で正解にたどり着いたチームはありません。** 第3回で習ったとおり、Problem も Solution も仮説です。大事なのは、正しさを言い当てることではなく、**次に確かめられる形にしておくこと**でした。

今日つくったものは、まだ実際の現場で使われていません。QUESTION が残っているのが正しい状態です。そこから先は、実際にその仕事をしている人に会いに行くところから始まります。

# 講師の事前準備

この時間配分は授業案です。**3限は予備8分、4限は予備10分**を含みます。

## 準備するもの

- **第7回用スターターの配布**。`constitution.md` が第2回版と違う（受け入れ条件1〜3項目、AC1は端から端まで、75分制約、localStorage まで）。**第2回のZIPを使わせないよう、URLをSlackに掲示する**
- **スターターの展開は、第7回の前にSlackで案内しておく**（第6回の終わりに口頭でも伝える）。当日のダウンロードと展開に時間を取られると、2節の20分が削られる。1節の冒頭で、全員が `/speckit-` を打てる状態かを確認する
  - 案内に含めるもの：ZIPのURL（Windows / Mac）、展開したフォルダ**そのもの**を Antigravity IDE で開くこと、`/speckit-` でコマンド一覧が出れば完了であること、**第2回のZIPではない**こと
- [絞り込みシート](./handout/scope-and-spec.md)と[相互確認シート](./handout/review-sheet.md)の印刷またはSlack掲示
- 絞り込みシートの**記入例**（本READMEの田中さんの例をそのまま使える）
- **「削るかどうかの問い」の実演**（2.3節）。2節に入る前に、ホテルの例で1回やって見せる。「通知がなくても、画面を切り替えれば清掃状態の読み取りは試せる。でも清掃状態そのものが出なければ試せない」——この線引きを一度見せると、学生が自分で判断できるようになる
- 第7回提出用のSlackスレッド
- 6節のペア（どのチームとどのチームが組むか）を事前に決めておく。5チームなので**1チームは講師が相手をする**
- 最終発表の時間管理（4分でベルを鳴らす等）

## 巡回で見ること

**3限2節が最優先です。** ここで絞れなかったチームは、まず間違いなく最後まで動きません。

| 優先 | 見ること |
| --- | --- |
| 1 | **①「今回確かめたいこと」が書けているか。** ここが空のまま受け入れ条件を書き始めたチームは、機能の一覧になる。戻らせる |
| 2 | **AC1が端から端まで通る条件になっているか。** 「押せる」「表示できる」で切れていたら直させる。ここが今日いちばん効く |
| 3 | **受け入れ条件が4項目以上になっていないか。** なっていたら、その場で削らせる。**確認例が複数あるのは問題ない** |
| 4 | **項目数が少なくても、1項目が広すぎないか。**「予約を管理できる」のような条件は、対象・場面・データを絞らせる |
| 5 | **「今回つくらないもの」が空でないか。** 空のチームは絞れていない |
| 6 | 確認例が書いてあるか（「〜できる」だけで止まっていないか） |
| 7 | `spec.md` の項目数が増えていないか |

3限4節（開発）からは、進め方も見る。

| 優先 | 見ること |
| --- | --- |
| 1 | **全員が同じ画面を見ているか。** 別々のPCで別々のことを始めていたら、1台に集めさせる |
| 2 | **見ている人が黙っていないか。** 黙っていたら、絞り込みシートを開かせて「ACに入っているか」を聞く役を渡す |
| 3 | **交代しているか。** 20分以上同じ人が操作していたら声をかける |

4限は、AC1 も通っていないチームを優先して支援する。**範囲を削る判断を、講師から促してよい。**

## 時間が押したときの削り方

| 優先度 | 扱い |
| --- | --- |
| 必ず残す | 2節の絞り込み、AC1が通ること、6節の相互確認、最終発表 |
| 短縮してよい | 3節の構成図の精度、成果物テンプレート7のビジネス価値の見直し、8節の通し練習（1回だけは残す） |
| 最後に削る | 10節の個人振り返り（事後学習へ回す） |

3限の予備8分は、**開発ではなく2節の絞り直しと仕様書の確認に充てる**。4限の予備10分は発表の押しに充てる。

## 講師2名の分担

- 3限2節は**2名とも絞り込みの巡回に入る**。ここが今日の成否を決める
- 4限6節は、5チームのうち余る1チームの相手を1名が務め、もう1名が全体の時間管理をする
- 最終発表は、進行・時間管理を1名、コメントと記録をもう1名

## 想定されるつまずき

| 症状 | 対処 |
| --- | --- |
| `/speckit-specify` が長い仕様書を返し、読む時間がない | 「受け入れ条件の節だけ読む」に切り替えさせる。4項目以上なら削る |
| AIが AC にない機能を実装してしまう | 4.3のプロンプトで一覧化させ、消す。消すとACが壊れるものは残してよい |
| AC1 が30分たっても通らない | 構成を捨てて、1ファイル（`index.html` のみ）で作り直させる。設計の美しさは今日の評価対象ではない |
