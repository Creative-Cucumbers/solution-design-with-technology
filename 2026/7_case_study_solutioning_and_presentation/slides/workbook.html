今日の問い：課題を見つけて、解いて、届ける。その一本を、自分たちで通しきれるか？

世の中の問題を見つける。その課題を解く。そして、人が使える形にして届ける。この一連が通って、はじめてソリューションです。 どれかひとつが欠けていると、良いアイデアも、よくできた資料も、誰の仕事も変えません。第1回から第6回まで、この流れを分けて学んできました。今日はその最後の区間です。

速くつくるのは、目的ではなく手段です。 今日は開発に75分しか使えません。けれどこれは速さを競うという意味ではありません。早く形にするのは、早く確かめるためです。頭の中にあるうちは、どんなアイデアも良く見えます。触れる形にして初めて、思っていたのと違うところが見えます。

要件と設計を先に押さえるのも、作業を速くするためではありません。 第2回の受け入れ条件、第4回のアーキテクチャ図。これらは、何を確かめたのかが分かる形にして、アイデアを進化させ続けるためにあります。決めずにつくったものは、動いても何が効いたのか分かりません。次に何を変えればいいかも分かりません。それは、学んだことを次に引き継げない試作です。

だから今日は、全部つくろうとせず、確かめたいことが分かる最小の形をつくります。絞ることは妥協ではありません。何を捨てたかを説明できることが、今日の成果物の一部です。

2. 受け入れ条件を絞り、仕様書にする (20分)

2.1 今日いちばん重要な20分です

絞るのは、時間が足りないからだけではありません。何を確かめたいのかを、先に決めるためです。

内訳は、考える8分 → 受け入れ条件に整理する7分 → 仕様書をつくって確かめる5分です。

全部つくって動いたとしても、何が効いて何が外れたのかは分かりません。条件を決めてからつくれば、動かしたときに「AC1は通った、AC2は思っていたのと違った」と言えます。次に何を変えればいいかが、手元に残ります。 それがアイデアを進化させる元手になります。

そのうえで、現実の制約もあります。第6回で出した解決策は、たいてい75分では終わりません。ここで絞らないと、どこも動かないまま発表を迎えます。

やることは一つです。絞り込みシートを埋めます。いきなり受け入れ条件を書くのではなく、「何を確かめたいか」から考えます。

絞り込みシート ──→ 要約を成果物テンプレート8「要件定義」に貼る
      │
      └──→ 確認例と制約を含むシート全文を /speckit-specify に貼る ──→ spec.md → plan.md → 実装

シートが源で、spec.md はそこから派生したものです。 順番を逆にしないでください。先に Spec Kit を回すと、AIが気を利かせて要件を増やし、75分では終わらない仕様書ができあがります。

2.2 まず「確かめたいこと」から考える（8分）

いきなり受け入れ条件を書き始めないでください。まず自分たちの言葉で考えて、そのあとで条件の形に整えます。

【前半】考える欄   ①〜⑥を順に埋める（チームで判断・必要に応じてAIに相談／8分）
                        ↓  AIに整理してもらう
【後半】渡す欄     受け入れ条件の形に整え、人間が確認する（7分）
                        ↓
            要約を成果物テンプレート8へ ／ 全文を /speckit-specify へ

項目数を3つにしても、つくる範囲が小さくなるとは限りません。 「予約を管理できる」は1項目ですが、登録・変更・キャンセル・重複防止まで含みます。数だけでなく、対象・場面・操作・データの広がりを絞る必要があります。①〜⑥は、そのための欄です。

絞り込みシートの前半を、この順に埋めます。まずチームで考えてください。 言葉にできない、選択肢が浮かばないときは、AIに相談してかまいません（2.6節）。ただし、採用する内容と理由はチームで決めてください。

② 今回扱う場面誰が、いつ、何をする場面だけをつくる？清掃担当が完了を記録し、フロントが確認する場面

④と⑤で迷ったら、一つずつこう聞いてください。

それを今回つくらなくても、①で書いた「確かめたいこと」は確かめられる？

答えどうするか
はい後回し、または模擬の候補。⑤で「代わりの方法で試す」か「今回は扱わない」へ

ホテルの例なら、通知がなくても画面を切り替えて清掃状態の読み取りは試せます。一方、清掃状態そのものが表示されなければ、確かめたいことが確かめられません。この違いが、残すか削るかの境目です。

模擬にしたものには、それによって確かめられなくなることを添えてください。

同じPCで担当を切り替える試作なら、表示の読み取りやすさは確かめられます。

けれど、実際の端末間での共有や、繁忙時の入力の手間までは確かめられません。

ここに書いたことは、成果物テンプレート11の QUESTION になります。

- 自分たちが決めていない機能が増えていないか

合わない箇所は自分たちで直します。次のルールが判断の基準です。

受け入れ条件は1〜3項目主要な流れを成立させる条件にまとめる。4項目目を足したくなったら「今回つくらないもの」へ送る
AC1は、端から端までAC1だけでも、その人に価値が届く流れが通ること。「入力できる」「表示できる」で切らない
主要な流れは一本分岐、管理画面、設定、権限、例外処理の網羅はつくらない
確認例は複数付けてよい1つの条件に確認を2〜3個書いてかまいません。正しく動くことを確かめる例（同じ操作を2回する、別の対象に誤って反映しないか）は、条件を増やすことではありません
間に合わないときは削る機能を足して解決しない。後ろの項目から落とす

AC1の切り方がいちばん大事です。 「清掃完了を押せる」で止めると、AC2を落としたときにフロントへ何も届かず、解こうとした課題が解けません。AC1だけ残しても、その人の仕事が少しよくなるところまでを1項目にしてください。

他の人が開いて動かせる形で出してください。 自分のPCでしか動かないと、評価できません。ZIPには「どのファイルを開けばよいか」「最初に何を入れればよいか」を書いた README.txt を1枚入れてください。

生成AIとのやりとりは、共有URLが作れるサービスならリンクを、作れない場合は判断に関わった部分の抜粋をテキストで出してください。全部のログは要りません。

AIが生成したコードや文章をそのまま出すだけでは、自分の理解は確認できません。採用した理由と、確認したことを自分の言葉で書いてください。

到達の目安

- つながっている：課題 → 解決策 → 動くもの → 確かめたこと、が一本の筋で説明できる。どこかが切れていたら、動いていても届いていません。

- 通っている：主要な利用の流れが一本、最後まで動く。AC1 が端から端まで通っていれば、動作面はそれで足ります。

- 説明できる：構成図を使って、情報がどう流れるかを説明できる。なぜその技術を選んだかを言える。

- 区別できている：観察した行動・言葉、その解釈、KEEP / CHANGE という判断、未確認の QUESTION が、混ざらずに分かれている。落とした機能とその理由が書いてある。

- 次がある：つくって分かったことから、次に何を変えるかが言える。

「AC1が通れば足りる」のは、動作面の最低到達条件です。 それだけで全体の評価が決まるわけではありません。上の5つは、根拠・説明・確認も含めてまとめて見ます。

逆に、AC1〜AC3 がすべて通っていても、課題とのつながりが説明できなかったり、確かめたことと確かめていないことが分かれていなければ、届いたとは言えません。

機能の数、画面の見栄え、AIの利用量では評価しません。 落とした機能が多いことも減点ではありません。判断の理由が書いてあるかを見ます。速くつくれたことも評価しません。 速さは、早く確かめるための手段です。

事後学習

- 未実装の範囲を1つ進める、または既存を確かめ直す（3時間程度）：次のどちらかを選んでください。

- 成果物テンプレート10に「実現できなかった」と書いたもののうち1つを選び、受け入れ条件を1つ書き足して実装する。何が難しかったかを記録する。

- 新しい機能は足さず、AC1〜AC3 の確認例を増やして確かめ直す。崩れた箇所と、直した内容を記録する。

「受け入れ条件は1〜3項目」は、授業中の75分に限った制約です。 事後学習で条件を足すのはかまいません。足すときは、spec.md と .specify/memory/constitution.md の記述も一緒に更新してください。制約を変えたなら、変えたことを書き残すのがルールです。

- QUESTION を1つ確かめる（2時間程度）：成果物テンプレート11に残した QUESTION のうち1つを選び、どうすれば確かめられるかを設計する（誰に、何を聞くか／何を観察するか）。実施は必須ではありません。

この演習のおわりに

7回を通して、次の一周を自分たちの手で回しました。

ユーザーを知る → 課題を定める → 解決策を選ぶ → 設計する → つくる → 確かめる → 更新する

一度で正解にたどり着いたチームはありません。 第3回で習ったとおり、Problem も Solution も仮説です。大事なのは、正しさを言い当てることではなく、次に確かめられる形にしておくことでした。

今日つくったものは、まだ実際の現場で使われていません。QUESTION が残っているのが正しい状態です。そこから先は、実際にその仕事をしている人に会いに行くところから始まります。
