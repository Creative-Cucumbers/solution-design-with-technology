# 講師向けメモ: 第4回 ソリューショニングとプロトタイピング

> このファイルは進行用です。学生向けの資料は [README.md](./README.md) です。

## 失敗の仕掛け: 「plan.md を読ませない」

第2回は**受け入れ条件を隠す**ことで失敗させた。今回は隠さない。**追加の要望3つは README に書いてある。** 代わりに、失敗の仕掛けはここに置く。

> **演習D-1では `/speckit-plan` を実行させるが、中身を読ませずに次へ進ませる。**

- Spec Kit の工程のうち、**設計（plan）だけを人が素通りする**状態を作る。仕様（spec.md）はあるので、第2回との差分が「設計の有無」だけに絞られる
- 要望を先に読まれても問題ない。**構造を決めていないこと自体が原因**なので、先読みしても設計は生まれない

読み上げるときに必ず言うこと:

- 「計画は読まずに進んでください。**今日はこれが実験の条件です**」
- 「できなくて構いません。**どこで止まったか**を覚えておいてください」
- （6節で）「**腕の問題ではありません。** 設計の話をするために、わざと設計を飛ばして始めました」

## 重要: 「AIが失敗すること」に賭けない

**この授業設計の最大のリスクは、AIが追加の要望を3つとも、きれいに実装してしまうことである。**
最近のエージェントは、データの形を作り直して動く状態まで持っていく確率が高い。そうなると学生の感想は「追加できた、便利」で終わり、**設計の必要性がまったく伝わらない。**

そこで5節は「**失敗を見せる**」設計をやめ、「**払ったコストを見せる**」設計にしてある。要望を入れたあと、必ず3つのチェックをやらせる。

| | チェック | 何が見えるか | AIが成功していた場合でも |
| --- | --- | --- | --- |
| A | 4.3で入れた**3件のデータが残っているか** | データの形が作り直されたかどうか | 消える／崩れることが多い。残っていてもBへ進むだけ |
| B | **AC1〜AC3がまだ通るか** | 回帰（動いていたものが壊れる） | 通っていてもCへ進むだけ |
| C | **AIに「何を書き換えたか」報告させる**（コードは触らせない） | 書き換え規模と、**データの形を誰が決めたか** | 「**私（AI）が判断しました**」と答える。ここが核心 |

そして最後に、**AIに聞かずに**答えさせる質問を置いてある。

> 「写真は1件につき3枚までにしてください」と言われたら、**どのファイルの、どこを直せばいいですか?**

**ほぼ全員が答えられない。** これは、AIの実装が成功していても成立する。
したがって5節の着地は「壊れた/壊れなかった」ではなく、**「動いているのに、自分では説明できない」**という一点に置く。

> [!IMPORTANT]
> 読み上げる言葉を固定しておく。
>
> - 「**動いたかどうかは、今日の論点ではありません。**」
> - 「入った人も、止まった人も、同じ状態です。**いま手元のアプリが、どういう作りなのか説明できない。**」
> - 「これは、次に何か頼まれるたびに、**AIに全部作り直してもらうしかない**ということです。」
> - 「**AIは決めてくれますが、覚えていてはくれません。**」

### 追加の要望が効く仕組み

| | 要望 | 触るところ | なぜ1行で済まないか |
| --- | --- | --- | --- |
| 追加1 | 写真を**複数枚** | データの形 | 単一の値を**配列**に変える。表示・追加・削除の全部に波及する |
| 追加2 | 受け取りの**履歴** | データの形 | 「状態」ではなく**別のまとまり（履歴）**が必要。持ち主・日時も要る |
| 追加3 | 絞り込み結果を**URLで共有** | 画面の責務 | 検索条件を画面のどこが持つかを決め直す。表示と検索の分離が要る |

**3つ同時に出すこと**が重要。1つずつなら凌げても、同時だと書き換え規模が大きくなり、チェックCの報告が効く。

> [!TIP]
> **逆に、ほとんど壊れなかった学生がいたら、それは良い教材になる。** 6節で指名して「AIは何行書き換えたか」「データの形は誰が決めたか」を読み上げさせる。
> 規模の大きさ（たいてい複数ファイル・数十行以上）と「AIが判断した」という答えが、そのまま次の話につながる。

## 4限の進行メモ

4限は**失敗を仕込まない。** 3限と逆に、ここは**成功してほしい場面**。統合がうまくいくことで、設計の価値が確定する。
そのために、**手順を細かく指定してある。** 自由にやらせると第2回の演習Cと同じ結末になる。

- **12節（持ち寄り・7分）**: 1人1分で紹介。聞く側に「**自分と違うところを1つメモ**」をやらせる。とくに**データの形**を見比べさせる。「同じお題なのに全員違う」を全体に確認させるのが目的
- **13節（設計合意・18分）**: 4ステップを**時計を見て区切る**。ここが4限の山場
  1. **ベースを1人の案に決める（4分）**。混ぜさせない。5分揉めたら「いちばん単純な案」で強制的に決めさせる
  2. **契約にする（6分）**。文章ではなく**コードに貼れるコメント**の形で書かせる。日付の形式まで決めさせる（ここを決めないチームは必ず統合で詰まる）
     - 合意確認は「**1人が読み上げ、他の人が画面と動きを言う**」。違う絵が出たら、そこが45分後に壊れる場所
  3. **ファイル単位で分担（4分）**。`data.js` の担当を最初に決めさせる。**同じファイルを2人で触らせない**
  4. **DoDと統合役（2分）**。統合役を決めないチームが出るので、机を回って確認する
  - 13節終了時に**成果物3つ（契約入り design.md / 担当者名入りの図 / 分担表と統合役）**が全員の画面にあるか確認してから次へ進む
- **14節（分担開発・20分）**: **11分 → 中間統合3分 → 修正6分**。この区切りがこの回の新しい仕掛け
  - 「`list.js` だけ作って。他は触らない」を**必ず言わせる**。範囲指定なしだと4人が4つのアプリを作ってしまう（最大の事故）
  - **11分で強制的に手を止めさせる。** 「動いていなくていい、いま集める」と宣言する。止めないと中間統合が消える
  - 集め方: 各自が**チームのSlackスレッドにファイルを貼る** → 統合役が1フォルダに集めて開く
  - **ここで動かないのが正解**と先に言う。目的はズレの早期発見
  - 修正のルールは「**契約から外れたほうが直す**」。契約自体が違っていたら全員で直して貼り直す
- **15節（統合・12分）**: 集めて動かす（5分）→ **受け入れ条件を全員で通す**（4分・1人が操作、他が見る）→ 振り返りメモ（3分）
  - 15.3のメモが16節の素材になる。**書かせてから**16節に入る
- **16節（なぜ難しいのか・13分）**: ここが今回追加した講義パート。**学生の体験に名前をつける作業**
  - 16.1で第2回の演習Cと並べる → 16.2で `n(n-1)/2`（人を足すと伝える量が増える／ブルックスの法則）
  - 16.3の表は**自分に起きたものに印をつけさせる**。挙手で数を数えると盛り上がる
  - 16.4のプラクティス表は、**「今日との対応」列を指差しながら**読む。今日やったことが全部プラクティスだったと分かるのが狙い
  - 16.5で「AI時代に効くのは**契約と自動テスト**」に絞り、18節のCI/CDデモへ渡す
- **18節（CI/CDデモ）**: 16.5の「ズレたら機械が止める」をそのまま受けて始める

## CI/CDデモの手順（18節・13分）

**事前に講師環境で1回通しておくこと。** 当日その場で作らない。

1. 準備（授業前）: 落とし物掲示板のリポジトリを用意し、受け入れ条件のテストとGitHub Actionsの設定を入れておく。**AIに書かせる様子も見せたいので、プロンプトは手元に用意する**
2. デモ:
   - ブランチを作って変更を push → **PRを作る**
   - Actions が走る様子を見せる（実行待ちの間に「CIのIは Integration」の話をする）
   - **わざと受け入れ条件を1つ壊して** push → 赤くなる → マージできないことを見せる
   - 直す → 緑 → マージ → 自動で公開される
3. 「やってみたい人は [ci-guide.md](./ci-guide.md) を見てください」で締める

> [!IMPORTANT]
> **約7割が前期Day5でGitHub push と Renderデプロイを経験済み。** 「公開できます」では新規性がないので、**検査が挟まること**を主役にする。残り3割にはアカウント作成から必要なので、授業内で全員にやらせない（ガイドに回す）。
