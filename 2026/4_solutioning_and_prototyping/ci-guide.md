# 検査してから、公開する（希望者向け）

第4回18節で実演した「**push したら検査され、通ったら公開される**」仕組みを、自分のチームでも試すための手順です。授業内では扱いません。できなくても成績には影響しません。

## 前期との違い

| 前期（アプリケーション開発演習 Day5） | ここでやること |
| --- | --- |
| push したら Render で公開される | push したら**検査してから**公開される |
| 動いているかは自分で見る | **受け入れ条件が自動で確認される** |
| 一人で push | **PRを出して、合格を確認してからマージ** |

## 用語

- **CI（継続的インテグレーション）**: 変更を頻繁に統合し、自動で検査して、壊れていないか早く気づく仕組み。**I は Integration＝統合**
- **CD（継続的デリバリー / デプロイ）**: 検査を通った変更を、自動で公開する仕組み
- **PR（プルリクエスト）**: 「この変更を取り込んでください」という依頼。検査の結果がここに表示される

## 手順

### 1. リポジトリを用意する

GitHubに新しいリポジトリを作り、チームのプロトタイプを push します。前期にやった手順と同じです。

### 2. 受け入れ条件から、テストを作る

AIに書かせます。渡すのは**受け入れ条件**だけです。

```
次の受け入れ条件を自動で確認するテストを書いてください。
ブラウザで動くHTMLアプリが対象です。

（受け入れ条件を貼る）

- テストの実行方法も教えてください
- 特別なインストールが少ない方法を選んでください
```

### 3. 検査の設定を作る

これもAIに書かせます。

```
GitHub Actions のワークフローを作ってください。
- プルリクエストが作られたときにテストを実行する
- テストが失敗したらマージできないようにしたい
設定ファイルの置き場所も教えてください。
```

> [!TIP]
> 置き場所は `.github/workflows/` の中です。AIが別の場所に作ろうとしたら、指摘してください。

### 4. 試す

1. ブランチを作って、変更を push する
2. GitHub上で**プルリクエストを作る**
3. 自動で検査が走る。緑なら合格、赤なら不合格
4. **わざと条件を1つ壊して**、赤くなるのを見る
5. 直して緑にする
6. マージする → 公開される

### 5. 公開をつなぐ

- **Render**: 前期と同じ。GitHubと連携すると、マージのたびに自動で反映されます
- **GitHub Pages**: ブラウザだけで動くアプリなら、こちらが簡単です。リポジトリの Settings → Pages から有効にします

## つまずいたとき

| 症状 | 対処 |
| --- | --- |
| Actions が走らない | 設定ファイルが `.github/workflows/` にあるか確認する |
| テストがいつも赤い | テストの書き方ではなく、**受け入れ条件が曖昧**なことが多い。条件を見直す |
| 秘密の情報を push してしまった | **すぐに講師に連絡してください。** パスワードやAPIキーは即座に無効化します（前期Day5で扱った内容です） |

分からないことは、Slackで聞いてください。
