**今日の問い：自分たちが知らない誰かの仕事を、本当に良くできるか？**

第1回から第5回までで学んだことを、今日と次回で全部使います。10のテーマから一つを選び、その仕事をしている人を具体的に思い描き、課題を定め、解決策を決めて、**実際に動くものをつくる**ところまで進みます。

**現実に向き合い、考え抜き、形にする。**

第6回は、ユーザーの仕事を知り、使い続けてもらえるソリューションを考え抜きます。一時的な便利さだけでなく、実際の仕事の流れに合い、継続して価値を届けられるかを考えます。第7回は、その解決策を要件・アーキテクチャに落とし込み、プロトタイプをつくって確かめます。

第6回と第7回、合わせて400分。**調べる・考える・つくる**の一周を、自分たちの手で回しきることが目標です。今日はそのうち「調べる・考える」を終わらせ、最後に中間発表をします。

### 1.2 前回までとのつながり

### 1.4 課題

> **あなたのつくるものが、誰かの「仕事」を変える。**
>
> 世の中には、あなたがまだ見たことのない仕事がたくさんあります。
>
> - 夜勤明けの看護師が、申し送りのために何を書き写しているか。
> - ホテルの清掃担当が、どの部屋が空いたのかを、どうやって知っているか。
> - 農場の出荷担当が、明日の人手を、何を見て決めているか。
>
> どれも毎日くり返されています。そして、そのうちのいくつかは「面倒だけど、そういうものだから」で片づけられたまま、何年も変わっていません。変える人がいなかっただけです。
>
> **今回の課題は、そこに手を入れることです。**
>
> 10のテーマから一つを選び、その仕事をしている人を一人、具体的に思い描いてください。毎日くり返している作業、見えなくて困っていること、伝わらずにやり直しになっていること。そのうちの一つに絞り、テクノロジーで解けるかを考え、**実際に動くものをつくって**ください。
>
> **条件は三つ。**
>
> 1. **思いつきではなく、調べたことから始めること。** 「こんなアプリがあったら便利そう」から入らないでください。まずその仕事を調べ、その人がどんな一日を過ごし、どこで手が止まっているのかをつかむ。提案の出発点は、あなたの思いつきではなく、その人の現実です。求人票を一枚開くだけでも、その仕事の一日が見えてきます。
> 2. **その人の仕事が、本当によくなると言えること。** 「あったら便利」では足りません。誰の、どの作業が、どう変わるのか。アプリでも、Webサービスでも、AIでも、データの使い方でも、IoTでもかまいません。ただし「運用を見直しましょう」「気をつけましょう」で終わる提案ではなく、技術が何を肩代わりするのかを説明できること。どのくらいよくなるのかを数字で言えると、提案はさらに強くなります。
> 3. **最後は、動くものを見せること。** 全機能はいりません。「その人がこれをする」という主要な流れが一本、最後まで動けば十分です。見栄えや機能の数では評価しません。企画書で終わらせず、手を動かして、触れるところまで持っていってください。
>
> この三つは、**調べる・考える・つくる**という一本の流れです。どれか一つだけが良くても、つながっていなければ意味がありません。調べたことが課題につながり、課題が解決策につながり、解決策が動くものになっている。その筋が通っているかを見ます。
>
> **AIは、その全工程で使ってください。** けれど、AIを使うことが課題ではありません。どの仕事を選び、どの課題に絞り、なぜその解決策にしたのか。その判断はあなたたちのものです。とくに調べるときは、AIに答えさせるのではなく、**読むべき資料を探させてください**。
>
> 最後にやるのは、提案の発表ではありません。**動くものを見せながら、「自分たちはこの人のこれを変えた」と言い切ること**です。

### 1.5 チーム編成

### 2.2 割り当て方

**1チーム1テーマ。チーム間で重複はできません。**

1. チームで**第1希望から第3希望まで**決めます（2分）。
2. Slackの第6回テーマ希望スレッドへ、**「チーム名＋第1希望の番号とテーマ名」**を投稿します。
3. **投稿時刻の早い順に確定**します。先に同じテーマが取られていたら、第2希望を投稿してください。

早く決めたチームが有利になります。迷ったら、**自分たちが一番「見てみたい」と思う仕事**を選んでください。「人気が出そう」「大きな市場だから」だけで選ばないでください。

### 2.3 職種と場面を一つに絞る

テーマが決まったら、**どの職種の、どの場面か**を一つに絞ります。ここが広いままだと、このあと全部が広くなります。

| | 悪い例 | 良い例 |
| --- | --- | --- |
| 対象 | 宿泊施設で働く人 | **ビジネスホテルのフロント担当** |
| 場面 | 業務全般 | **清掃が終わった部屋を、チェックイン前に把握する場面** |

絞るときの基準は4つです。

1. 具体的な職種と、一つの利用場面に絞れている。
2. 公開情報・自分たちの経験・身近な人への確認など、調べる手がかりがある。
3. テクノロジーが課題解決の中核を担い、技術によって何が可能になるかを説明できる。特定の製品・技術を先に決める必要はありません。
4. 200分後（第7回の終わり）に、主要な体験を試作して実際に動かせる範囲である。

決まったら、**スライド3（課題の背景と目的）**に、選んだテーマ・対象の職種と場面・選んだ理由を書いてください。まとまらないときは講師を呼んでください。範囲を絞る手伝いをします。

## 3. 対象の仕事を調べる (25分)

### 3.1 AIに「業務の実態」を直接答えさせない

選んだ職種は、おそらく**あなたが一度もやったことのない仕事**です。だからAIを使って調べます。ここまでは前提です。

問題は聞き方です。AIに「この職種は1日に何件くらい対応しますか」と聞けば、もっともらしい数字が返ってきます。**それは出典のない生成結果です。** そのまま書くと、ペルソナも課題も、最後のビジネス価値の計算も、全部その数字の上に建つことになります。

第3回で習った区別をそのまま使います。

| | 意味 | 書き方 |
| --- | --- | --- |
| **FACT** | 公開情報で確認できたこと | 出典URLを添える |
| **ASSUMPTION** | AIや自分たちが補った、まだ確かめていないこと | 「〜だろう」と分かる形で |
| **QUESTION** | 確かめられなかったこと | 空欄にせず、そのまま残す |

第5回の「**Dataは事実。Insightは解釈。Problemは仮説。**」も同じ区別です。

### 3.2 手順

**① AIに探させる（5分）**

AIに答えさせるのではなく、**読むべき資料を探させます**。

```
ビジネスホテルのフロント担当の仕事について書かれた公開情報を探してください。
求人票、業務マニュアル、業界団体の資料など、実際に読めるページのURLを挙げてください。
1日の流れ、使っているツール、他の担当者とのやり取りが分かるものを優先してください。
```

**② 自分たちで開いて確認する（10分）**

挙がったURLを、**最低1件は実際に開いて読みます**。読んでいないものをFACTにはできません。

このテーマ群では**求人票が一番使えます**。業務内容、使っているツール、1日の流れ、求めるスキルが具体的に書かれていて、数もあります。

| テーマ | 求人票に加えて見られるもの |
| --- | --- |
| 1 大学職員 | 各大学が公開する業務改善・DX推進の報告資料 |
| 2 医療従事者 | 看護業務の改善事例・学会発表、病院が公開する取り組み |
| 3 宿泊施設で働く人 | 宿泊業の生産性向上に関する官公庁・業界団体の資料 |
| 4 小売業で働く人 | 小売DXに関する官公庁資料、チェーン各社の採用ページ |
| 5 製造業で働く人 | ものづくり白書、工場の改善事例記事 |
| 6 物流を支える人 | 物流効率化に関する国土交通省資料、2024年問題のレポート |
| 7 自治体職員 | 自治体が公開する業務棚卸し・BPR資料、DX推進計画 |
| 8 クリエイティブ制作に関わる人 | 制作会社の業務紹介、業界メディアの制作フロー解説 |
| 9 建設・設備管理に関わる人 | 建設DXに関する国土交通省資料、点検業務の事例記事 |
| 10 農業に関わる人 | スマート農業の実証事例、生産者本人の発信 |

**③ スライド4にまとめる（10分）**

記入形式の例（テーマ3・ビジネスホテルのフロント担当）：

以下は説明用の仮想例です。FACT欄の空欄は、自分たちが実際に読んだ資料の内容とURLで置き換えてください。ホテルの設定や仮説を、確認済みの事実として使わないでください。

```
FACT  公開情報で確認できたこと
・［実際に読んだ資料に書かれている業務内容］
  出典：［資料名・実際に開いたURL］
・［別の確認できた記述。分かる範囲で対象の職場や条件も記す］
  出典：［資料名・実際に開いたURL］

ASSUMPTION  AIや自分たちが補った、まだ確かめていないこと
・清掃完了の連絡は、内線か口頭で届いているのではないか
・10時〜15時の間に、同じ部屋の状態を何度も確認し直しているのではないか

QUESTION  確かめられなかったこと
・清掃担当とフロントは、1日に何回やり取りするのか
・早めに到着した客を待たせる時間は、実際どのくらいか
```

### 3.3 ここで得られるものの限界

この手順を踏んでも、得られるのは「**その職種の一般的な業務の理解**」であって、特定の現場の実態ではありません。それでかまいません。

**調べ方に限界があることを自覚して書くこと自体を、成果物の一部として扱います。** QUESTIONの数ではなく、確認できた根拠と未確認事項を区別し、次に何を確かめるかを説明できることを評価します。

## 4. ペルソナを定める (20分)

第5回の **Personaの基本フォーマット**をそのまま使います。Personaは「人物紹介シート」ではなく、**USERについて考えるための仮説の集合**です。

| | 項目 | 書くこと |
| --- | --- | --- |
| 1 | 属性・役割 | どんな仕事と責任を持つ人か |
| 2 | 行動 | 日々どう働き、誰と関わるか |
| 3 | 思考 | 何を考えているか |
| 4 | 目的・Need | 何を達成したいか／何を避けたいか |
| 5 | 困りごと・制約 | 何に阻まれているか |

記入例（成果物テンプレートのスライド5）：

以下の田中さんは説明用の仮想人物です。年齢・客室数・担当業務も仮の設定です。実際の成果物では、確認済みの記述にだけ出典付きのFACTを付け、同じ項目に仮説が混じる場合は文を分けてください。

```
ペルソナ名：田中さん

1. 属性・役割  34歳。客室60室のビジネスホテルのフロント担当。
               日勤。チェックイン対応と予約管理を担当している。〔ASSUMPTION: 仮の設定〕
2. 行動        PMSと内線電話を行き来している。
               清掃担当から「終わりました」の連絡を内線で受ける。〔ASSUMPTION〕
3. 思考        早く着いた客を待たせたくない。
               確認ミスで同じ部屋を二重に案内したくない。〔ASSUMPTION〕
4. 目的・Need  いま入れる部屋がどれか、聞かずに分かる状態でいたい。〔ASSUMPTION〕
5. 困りごと・制約  清掃状況が内線でしか分からず、繁忙時はつながらない。〔QUESTION: 未確認〕
```

**各項目に FACT / ASSUMPTION / QUESTION のどれかを付けてください。** 3節で調べたことと、ここで補った仮説を区別するためです。第3回の「わかっている情報と、補った仮説を区別する」と同じことです。

「分からない」も残してください。空欄にするより、QUESTIONとして残っているほうが価値があります。

## 5. 着目する課題を決める (20分)

### 5.1 Problemはひとつじゃない

第3回でやったとおり、同じUSERからいくつもの課題候補が生まれます。**まず3つ以上出してから、1つ選んでください。**

AIにも候補を出させてかまいません。ただし**AIが最初に挙げた課題をそのまま採用しないでください**。よく語られている課題は、すでに製品が存在する領域であることが多く、気づかないまま「電子カルテをつくります」のような、既存製品の作り直しに向かいます。

### 5.2 「したいこと」を、何が邪魔しているか

第5回の形です。困りごとを並べる前に、**この人が本当は何をしたいのか**を書きます。そのうえで、それを邪魔しているものを課題にします。

```
INSIGHT     田中さんは本当は、聞かなくても部屋の状態が分かる状態でいたい。
PROBLEM     しかし清掃完了が内線でしか伝わらず、繁忙時に確認が滞るため、
            それが難しい。
```

### 5.3 PROBLEM HYPOTHESIS

選んだ課題を、第3回の型で1文にまとめ、**スライド6**に書きます。

```
私たちは、＿＿＿＿＿＿＿＿＿＿＿＿ というProblemを解く。

なぜなら、＿＿＿＿＿＿＿＿＿＿＿＿（このUSERにとって、大切な理由）
```

正解ではありません。**現時点で、私たちが解くべきだと考えるProblem**です。

選ばなかった候補も消さずに残してください。4限で案を比べるときに使います。

## 6. 講師へのチェックイン (5分)

各チーム**1分**で、次の2つを共有してください。

1. 誰を対象にしたか（ペルソナを一言で）
2. どの課題に着目したか

講師が進捗と困りごとを把握し、4限でどのチームを重点的に支援するかを決めます。資料は作らなくてかまいません。画面を見せながら話してください。

> **予備の10分について。** 3限には予備が10分あります。使わなければ3節のリサーチか5節の課題検討に充ててください。時間が押しているときは、ペルソナの項目を埋めきることより、**FACTが1件でもURL付きで残っていること**を優先してください。

# 4限目: 解決策を決め、中間発表する

| # | 内容 | 時間 | 形式 |
| --- | --- | --- | --- |
| 7 | 解決策の案を出す | 15分 | 個人5分（NO AI）＋チーム10分 |
| 8 | 案を比較し、一案を選ぶ | 20分 | チーム |
| 9 | 主要な利用の流れをラフに描く | 15分 | チーム |
| 10 | 中間発表の準備 | 10分 | チーム |
| 11 | 中間発表・質疑 | 30分 | 全体 |
| | 予備 | 10分 | |
| | **合計** | **100分** | |

## 7. 解決策の案を出す (15分)

### 7.1 最初の5分は、AIを使いません

第3回のアイディエーションと同じ形でやります。

> **5 MINUTES ／ 全員が書く ／ 1アイデア＝1枚 ／ NO AI**

- **全員が書きます。** 話す前に書いてください。
- **1つのアイデアを、1枚に。** 文字でも絵でもかまいません。
- **ダメなアイデアはひとつもありません。** 実現可能性は後で考えます。
- 勝つのは、**一番たくさん出したチーム**です。

5分経ったら、チームで数を数えて、互いの案を短く共有してください。

### 7.2 残り10分はAIで広げる

自分たちで出しきってから、AIに渡します。第3回のとおり、AIに渡すのは「答え」ではなく、**ここまで考えた仮説**です。

```
【USER】誰のため      ：ビジネスホテルのフロント担当 田中さん（34歳）
【PROBLEM】何を解く   ：清掃完了が内線でしか伝わらず、繁忙時に確認が滞る
【USER VALUE】どう良くなる：聞かなくても部屋の状態が分かる

この文脈で、私たちが出していない解決策の方向性を5つ挙げてください。
それぞれ、技術が何を肩代わりするのかを1行で書いてください。
```

AIは**仮説を広げる相手**であり、**自分たちの考えと比べる相手**です。出てきた案をそのまま採用せず、自分たちの案と並べてください。

## 8. 案を比較し、一案を選ぶ (20分)

### 8.1 比べる基準は3つ

第3回で使った基準をそのまま使います。

| 基準 | 問い |
| --- | --- |
| **User Value** | このUSERの仕事が、どう良くなる？ |
| **Originality** | これまでと違う、嬉しい体験があるか？ |
| **Feasibility** | どうすれば実現できそうか？ |

**多数決では決めません。** 「私は、これが好き」ではなく、**ペルソナを根拠に**「このUSERに、どんな価値があるか」を話し合って選んでください。

### 8.2 SOLUTION HYPOTHESIS

選んだ案を、第3回の型で1文にまとめ、**スライド7**に書きます。比較した案と、選ばなかった理由も一緒に残してください。

```
このUSERが ＿＿＿＿＿＿＿＿＿＿ できるように、

＿＿＿＿＿＿＿＿＿＿ というSolutionを試したい。

なぜなら ＿＿＿＿＿＿＿＿＿＿。
```

### 8.3 ビジネス価値（必須ではありませんが、できるだけ書いてください）

事業計画や市場規模の予測は求めません。**一人・一店舗・一社あたり**で考えてください。書けなかった項目は「未検討」と残してかまいません。

- 誰が使い、誰が対価・予算を出すか。
- 現在のやり方と比べ、何がどの程度よくなるか。
- 時間・費用の変化を、前提付きで概算する。

今回のテーマはどれも仕事の課題なので、「**その人の時間が何分浮くか**」から入ると書きやすいはずです。

> 例：1日20分×月20日の作業削減＝月約6.7時間。時給1,500円と仮定すれば約1万円相当の作業時間。
>
> ただし、時間削減がそのまま現金の削減になるとは限りませんし、この額が価格でもありません。**数字には必ず出典か仮定を書いてください。**

20分で比較まで終わらないチームは、予備の10分をここに充ててください。

## 9. 主要な利用の流れをラフに描く (15分)

**「その人がこれをする」という流れを一本**、ラフに描きます。画面のラフでも、操作の順番を並べた図でもかまいません。きれいに描く必要はありません。

```
例：田中さんが、いま入れる部屋を確認する流れ

  ① 清掃担当が、自分の端末で「502号室 清掃完了」を押す
      ↓
  ② フロントの画面の502号室が、グレーから緑に変わる
      ↓
  ③ 田中さんが画面を見て、早着の客を502号室へ案内する
```

これは成果物テンプレートの必須スライドではありませんが、**発表資料に1枚足してください**。第7回の開発時間は75分しかありません。白紙から始めるか、この下絵から始めるかで、到達点が変わります。

## 10. 中間発表の準備 (10分)

**スライド3〜7**を整えます。新しく資料をつくる必要はありません。ここまでに書いてきたものを、人に見せられる状態にするだけです。

発表の前に、チームで次を確認してください。

- [ ] スライド4に、**URL付きのFACTが1件以上**あるか
- [ ] ペルソナの各項目に、FACT / ASSUMPTION / QUESTION が付いているか
- [ ] 選んだ課題が1つに絞れていて、「なぜなら」が書けているか
- [ ] 案を複数比べ、選んだ理由が User Value で説明できるか
- [ ] 9節のラフが1枚あるか

## 11. 中間発表・質疑 (30分)

**5チーム×5分**（発表3分・質疑2分）＋入れ替え・講評5分。

### 11.1 発表すること

| | 項目 |
| --- | --- |
| ① | テーマ・対象の職種と場面 |
| ② | ペルソナ |
| ③ | 着目した課題と根拠（FACTとASSUMPTIONを分けて） |
| ④ | 案の比較と、選んだ理由 |
| ⑤ | 主要な利用の流れのラフ |
| ⑥ | ビジネス価値（書けた範囲で） |

3分です。全部を丁寧には話せません。**③と④に時間を使ってください。**

### 11.2 聞く側がやること

第3回でやったとおり、**感想より、問いを返します**。

| 問い | 何を確かめているか |
| --- | --- |
| **User Valueは？** | このSolutionで、USERの仕事や行動はどう良くなる？ |
| **Assumptionは？** | まだ確かめていない前提は何？ |
| **何を確かめたい？** | 次に聞くこと・試すことは何？ |

「いいと思います」は問いではありません。他チームの発表を見ることも、自分たちの仮説を深める時間です。

言われたことは、そのまま修正リストにしないでください。**なぜそう言われたのか**を考えて、変えるかどうかは自分たちで決めます。

# 課題と評価

## 提出物

Slackの第6回提出用スレッドへ、**第7回の前日まで**に投稿してください。

| 提出単位 | 提出物 | 評価すること |
| --- | --- | --- |
| **チーム** | 成果物テンプレートのスライド1〜7（PDFまたは共有リンク） | 対象・課題・解決策が一本につながっているか（観点2・3） |
| **チーム** | スライド4のFACT / ASSUMPTION / QUESTION | 根拠と仮説を区別しているか（観点2） |
| **チーム** | スライド7の案の比較と選択理由 | 複数案を同じ基準で比べ、選択を説明できるか（観点5） |
| **チーム** | 9節のラフ（1枚） | 主要な利用の流れを一本に絞れているか（観点3） |
| **全員個別** | 下の3点を、自分の言葉で | 自分の判断を説明できるか（観点2・4） |

個人の3点は次のとおりです。長さは各2〜3行で十分です。

1. **自分が担当した部分** — チームの中で何をやったか。
2. **自分が判断したことと、その根拠** — どの場面で何を選び、何を根拠にしたか。チームの結論と自分の考えが違っていてもかまいません。違ったことと、その理由を書いてください。
3. **次に確かめたいこと** — まだQUESTIONのまま残っていることを一つ。

AIが書いた文章をそのまま貼るだけでは、自分の理解は確認できません。採用した案やAIの出力を使った場合も、**なぜそれを選んだか**を自分の言葉で書いてください。

## 到達の目安

- **絞れている**：対象が「どの職種の、どの場面か」まで具体的で、課題が1つに決まっている。
- **区別できている**：確認できたこと（FACT）、補った仮説（ASSUMPTION）、分からないこと（QUESTION）が分かれている。
- **説明できる**：複数案を同じ基準で比べ、なぜその一案なのかをペルソナを根拠に説明できる。

資料の枚数、見栄え、AIの利用量では評価しません。QUESTIONが残っていることは減点ではありません。

## 事後学習

- **つくる範囲を決めておく（2時間程度）**：第7回の開発時間は**75分しかありません**。9節のラフのうち、どこまでを動かすかを決め、優先順位をつけておいてください。「全機能」ではなく「主要な流れ一本」です。
- **中間発表で受けた問いへの対応（1時間程度）**：出された問いのうち、変えるものと変えないものを分け、変えないものはその理由を書いてください。

第7回に追加作業を前提とした計画は立てないでください。**授業時間内に到達できる範囲**で決めてください。

## 次回予告

第7回「ケーススタディ: ソリューショニングと成果発表」では、今日決めた一案を実際に開発します。要件定義とアーキテクチャ図（第2回・第4回の内容）を書いてから実装し、受け入れ条件と照らして確認し、最終発表をします。

**動くものを見せながら、「自分たちはこの人のこれを変えた」と言い切る**のが到達点です。

| 優先度 | 扱い |
